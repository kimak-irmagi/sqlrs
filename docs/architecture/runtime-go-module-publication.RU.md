# Runtime Go: выпуск уже проверенного коммита

Статус: направление, подробное устройство и проверки MP01-MP12 согласованы
@evilguest 16 октября 2026 года для #151. Реализовано и проверено локально;
PR автоматизации, его CI и настоящий выпуск ещё впереди. Прежнее предложение
подготовительного PR заменено;
API библиотеки и правило неизменяемых выпусков сохраняются.

## Договор ручного запуска

Запускается release-runtime-go.yml из main. Версия инструментария H фиксируется
при запуске, а исходный коммит публикуемой библиотеки S задаётся отдельно.

| Параметр | Правило |
| --- | --- |
| operation | validate по умолчанию — только проверки; publish — публикация; verify — проверка уже опубликованной версии без записи тегов и файлов выпуска. |
| version | Точная v0.MINOR.PATCH или v0.MINOR.PATCH-rc.N, без ведущих нулей; N начинается с 1. |
| commit | Полный строчный 40-значный шестнадцатеричный S. Не имя ветки, тег, сокращение или неявная последняя версия. Коммит должен находиться в main и иметь успешный CI после слияния именно для S. |
| notes | Описание кандидата в Markdown, обязательное при validate/publish; до 16 КиБ UTF-8. Для verify и любых операций окончательной версии пусто. Это данные, не команды оболочки. Файл RELEASE-version.md в S не нужен. |
| candidate_version | Точная версия кандидата того же семейства, обязательная для всех операций окончательной версии; для операций кандидата пуста. Описание берётся из его публикации. Номер запуска и артефакт не передаются. |

Кандидат и окончательная версия выпускаются двумя явными запусками, без PR,
коммита и локальной копии репозитория между ними. Например: опубликовать
v0.6.0-rc.1 из S, дождаться успеха, затем опубликовать v0.6.0 из S, передав
candidate_version=v0.6.0-rc.1. После ошибки инструментария verify проверяет
прежнюю неизменяемую публикацию. Кандидат повторно проверяется в текущем
запуске; артефакты прошлого CI не дают разрешения на окончательный выпуск.

## Взаимодействия и полномочия

1. Получить проверенный инструментарий H и исходники S в разные каталоги.
   До любых публикаций отклонить запуск не из main, неверные параметры,
   отсутствие успешного CI для S, защиты тегов, нужных исходных файлов или
   совместимого договора модуля. Только явный ответ об отсутствии объекта
   нужного API означает отсутствие; неоднозначная ошибка чтения, доступа,
   ограничений или связи не считается отсутствием или успешной проверкой.
2. Проверить именно S инструментами из H: тесты Go из S, точное покрытие,
   гонки, случайные входы, эталоны, зависимости и внешнего потребителя через
   временный прокси. Тесты инструментария выполняются из H; задачи проверки
   исходников не получают учётных данных публикации. Нельзя проверить одну копию,
   а упаковать другую. Обязателен случай H != S: в S нет нового помощника
   выпуска и файла описания версии.
3. Для окончательной версии задача verify-candidate без прав записи полностью
   проверяет опубликованного кандидата: семейство, признак предварительной
   версии, точный S, защиту тега, описание и служебное окончание, файлы
   происхождения, загрузку через публичный прокси и базу сумм, отзыв прежней
   версии, контракты и чистого потребителя. Публикация зависит от успеха этой
   задачи в текущем запуске, не от тега или старого отчёта. Отсутствующий,
   неопубликованный, конфликтующий или не прошедший проверки кандидат блокирует
   выпуск. Суммы кандидата и окончательной версии проверяются отдельно, не на равенство.
4. Только publish получает contents:write для GITHUB_TOKEN; замены на личный
   токен или токен приложения нет. До создания нового точного тега на S проверить всё
   существующее состояние и размеры передаваемых данных. Тег нельзя заменять
   или удалять.
   Создать черновик выпуска, добавить и проверить прежнее детерминированное
   подтверждение происхождения и его контрольную сумму, затем опубликовать.
   Запуски одной версии выполняются последовательно, активный не отменяется.
   Несовпадение цели тега, описания, состояния или файлов останавливает выпуск.
   GitHub может заменить ожидающий запуск более новым: не обещается бесконечная
   очередь или строгий порядок поступления. Повторный запуск проходит те же проверки.
5. Повтор может продолжить совпадающий незавершённый черновик и добавить только
   недостающие файлы. Совпадающий опубликованный результат проверяется без
   перезаписи. Иное описание, конфликтующие файлы или другой S нельзя исправлять
   заменой уже существующего содержимого.
6. Проверить точную публичную версию с GOWORK=off, публичными GOPROXY/GOSUMDB,
   без replace и соседних исходников, существующим внешним потребителем из S.
   Сверить контрольные суммы, цель тега, происхождение, описание, отзыв прежней
   версии и обязательные обозначения контрактов. Ожидание распространения
   ограничено. Ошибка не меняет координату версии и не создаёт подтверждения успеха.
7. После всех проверок сохранить диагностический отчёт данной попытки;
   вывести версию, S, H, контрольные суммы и ссылку на запуск. Для приёмки нужен
   успех всего процесса. Отчёт — свидетельство, не разрешение или обязательный
   вход другого запуска. При ошибках сохраняются подробные журналы.

Описание состоит из переданного Markdown и служебного окончания с S и
действующими/историческими обозначениями контрактов. Пользовательский текст
не может подменить это окончание. Окончательная версия наследует точное
проверенное описание кандидата; название, версия и тег — отдельные поля GitHub.
Размеры считаются в байтах UTF-8, не символах JavaScript: описание до 16 КиБ,
полный текст со служебным окончанием до 20 КиБ, каждый готовый JSON запроса
записи выпуска до 128 КиБ. Всё вычисляется до первой записи, включая повторы
и окончательный выпуск. Экранирование, управляющие символы и многобайтовый текст
не должны вызывать ошибку размера уже после создания тега. Отчёт хранит хеш
описания, не ещё одну экранированную копию; срок хранения не влияет на выпуск.
Описание и результаты остаются в GitHub Releases/Actions, не требуют нового
исходного коммита. Для следующих выпусков не нужны PR с номером версии
или изменения дорожной карты.

## Правила токена и риск ограничения платформы

Новый процесс становится только ручным. В S может остаться прежний процесс
по событию тега, но события от GITHUB_TOKEN его не запускают. Используется
именно этот токен с явным contents:write, не личный токен или токен приложения.
Автоматическая замена токена, пробные теги и изменение настроек репозитория
не входят в проект. Проверки исходников и verify не получают права записи.

GitHub описывает дополнительные права для некоторых способов создания выпуска.
Первоначальное объявление уточняет условие: целевой коммит меняет процесс CI
и ещё не имеет ссылки ветки или тега. Наш порядок иной: сначала создать точный
тег через Git Refs, проверить его цель S, затем создать выпуск по существующему
тегу без target_commitish. По документации этот параметр не используется,
когда тег уже существует. Нельзя позволять созданию выпуска неявно создавать
тег или подставлять другую цель ради обхода отказа. Из этого ограничения
не следует запрет на коммиты определённого возраста или любой коммит не на HEAD.

Это основной способ реализации, не доказательство реальных прав. validate
и подставные ответы не проверяют разрешение настоящей записи. Его подтвердит
первый реальный выпуск кандидата после согласования и всех проверок. Отказ
создания тега останавливает процесс до выпуска; более поздний отказ может
оставить публичный тег или черновик и фиксируется как частичный сбой, не успех.
S и существующие версии сохраняются. При настоящем ограничении дополнительные
учётные данные или смена S требуют нового согласования. Одного прежнего вывода
из документации недостаточно для блокировки реализации. Старые теги и выпуски
продуктов остаются нетронутыми.

## Поиск состояния и восстановление

До записи тега уполномоченный издатель читает все страницы списка выпусков
с видимостью черновиков и все файлы подходящего выпуска по его id. Публичный
поиск по тегу не доказывает отсутствие черновика. Дубликаты, неполная видимость,
неверный ответ или неоднозначная ошибка блокируют публикацию. Ответ 404 при
создании или изменении — ошибка, не доказательство отсутствия объекта.

Различаются состояния: ничего нет; есть только совпадающий тег; совпадающий
черновик без тега или с совпадающим тегом; совпадающий опубликованный выпуск;
конфликт. Тег должен указывать на S, а черновик без тега — явно задавать S.
До записи сверяются точные тег, название, описание, признаки черновика и
предварительной версии, байты каждого существующего файла. Неизвестные файлы
и неполный опубликованный выпуск считаются конфликтом. Создание и публикация
задают make_latest=false, не заменяя последний выпуск продукта. В совпадающий
черновик можно добавить недостающие файлы и перевести его в опубликованный.
Описание и загруженные файлы не перезаписываются. Опубликованное только проверяется.
После ответа о конфликте или конкурентной записи состояние читается заново;
продолжение возможно только после полной сверки. Потерянный ответ не означает,
что запись не состоялась. Отказы после тега, черновика, каждой загрузки,
публикации и публичной проверки проходят тот же порядок восстановления.

Черновик не скрывает модуль Go: публичный тег уже открывает координату версии.
Поэтому проверки исходников, кандидата, описания, размеров и существующих
объектов предшествуют тегу. Последующая ошибка не разрешает откат или замену тега.

## Компоненты и владение данными

- release-runtime-go.yml задаёт задачи проверки и публикации, их права,
  получение H/S, проверки исходников, передачу ограниченных данных и зависимости.
- scripts/maintenance/runtime-go-release.mjs проверяет параметры, состояния
  выпуска, собирает описание и работает с узкой частью GitHub API. Правила
  проверяются без настоящих записей в GitHub. Ошибки не печатают токены или
  переданное описание. Помощник исполняется из H.
- runtime-go-release-cli.mjs связывает параметры и файлы запуска с этими
  правилами. Общая составная задача runtime-go-public-consumer повторно
  использует проверки публичного потребителя для кандидата и целевой версии.
  Оба средства принадлежат H.
- Проверяющие средства, расчёт покрытия и генератор происхождения берутся из H
  с явным корнем исходников S. Поиск через Git также ведётся в S, не в каталоге
  инструмента. H задаёт алгоритмы; S — код и тесты Go, примеры потребителя,
  манифест и ожидаемые эталоны. Исправление инструментария в H должно работать
  без добавления скриптов в S и подмены его примеров кодом библиотеки из H.
  Прежний формат подтверждения происхождения сохраняется; новых зависимостей
  и форматов Runtime нет. Неподдерживаемые исходники отклоняются до записи.

Доверенные администраторы и инструментарий остаются границей управления.
Отчёт сверяет содержимое и состояние запуска, но не даёт криптографической
защиты от администратора, который сам меняет процесс или правила публикации.

Диагностический отчёт содержит модуль, версию/тег, S/H, запуск/попытку, операцию,
хеш описания, суммы и результаты проверок. Схема разрешений по отчётам прошлых
запусков и её разборщик не вводятся. Имя артефакта включает run_attempt.
Выходы задач исходников — ограниченные данные, повторно проверяемые H; они
не становятся командами или импортируемым кодом в задаче с правами публикации.
Один ограниченный план и временные файлы существуют в памяти
и на диске запуска; теги, выпуски, их файлы и артефакты CI хранятся в GitHub.
Новая база данных не нужна.

## Границы приёмки

Разовое изменение автоматизации проходит обычный PR и CI. Оно не обязано
входить в S. Для #151 запрошен коммит слияния #152
892a5007adf4d499fbfbd7861569861ff11c43a8; первый реальный выпуск также проверяет
права платформы. Подмена на слияние автоматизации не допускается. Из этого S
выпускаются v0.6.0-rc.1 и v0.6.0. #151 закрывается только после проверок
окончательной публичной версии и отчёта в GitHub, не при слиянии автоматизации.
Обновление потребителей, исполнитель и подключение к приложениям не входят.
