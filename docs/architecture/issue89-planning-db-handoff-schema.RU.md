# #89 O5: удержание БД планирования и передача первой сессии — схема

Статус: схема утверждена @evilguest 2026-11-12 после критического и повторного
разбора. [Компоненты O5](issue89-measured-overhead-reduction.RU.md) утверждены.
DDL, эталонный каталог, писатели журнала и передача координатора реализованы
по утверждённым PG01–PG10 / OT-PG01–OT-PG02. После CP2 новые файлы O5
прошли локальный минимум покрытия; настоящая приёмка в Actions ещё открыта.

## 1. Представление и владение

Одна новая таблица `prepare_liquibase_planning_db_ownership`; новая физическая
копия, переименование БД и фиктивный новый владелец операции не создаются.
Точные наблюдения — в прежнем append-only `prepare_attempt_evidence`.

| Поле | Ограничение / назначение |
| --- | --- |
| job_id | TEXT PK, FK prepare_jobs(job_id) ON DELETE CASCADE. |
| task_id | TEXT NOT NULL CHECK = 'plan'. |
| attempt_no | Положительное целое; составной FK job/task/attempt к prepare_step_attempts ON DELETE CASCADE. |
| clone_id | TEXT NOT NULL UNIQUE; FK prepare_clones(clone_id) ON DELETE CASCADE. |
| retained_evidence_id | Положительный UNIQUE FK prepare_attempt_evidence(evidence_id) ON DELETE CASCADE. |
| plan_digest | NOT NULL канонический SHA256; неизменяемый сохранённый план. |
| session_id | Nullable UNIQUE TEXT; FK prepare_liquibase_sessions(session_id) ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED. |
| first_task_id | Nullable TEXT; составной FK job/task к prepare_tasks. |
| first_execution_digest | Nullable FK prepare_execution_bindings(execution_digest). |
| transferred_at | Nullable проверенный UTC, однократная запись. |
| disposal_requested_evidence_id | Nullable UNIQUE FK prepare_attempt_evidence(evidence_id) ON DELETE CASCADE. |
| disposal_evidence_id | Nullable UNIQUE FK prepare_attempt_evidence(evidence_id) ON DELETE CASCADE. |
| disposed_at | Nullable проверенный UTC, однократная запись. |

Четыре поля передачи либо все NULL, либо все заполнены. Передача исключает
запрос/доказательство/время удаления. Доказательство удаления и disposed_at
либо оба NULL, либо заполнены при прежнем запросе удаления. Запрос без
завершения — явно незаконченная очистка, не отсутствие. Изменяемая фаза не нужна:
удержание/передача/очистка-запрошена/удалено выводятся из этих сочетаний.
Исходные идентичности неизменяемы; переходы нельзя очищать, заменять или
перенаправлять. UPDATE без изменения не создаёт нового основания.

Полный ID БД, имя, operation_ref, target_path, источник и идентичность уже
закреплены неизменяемым фактом удержания, копией и управляемой привязкой.
Дублировать значения в таблице не нужно. Постоянного FK исторических фактов
к managed_runtime_operations, states или instances нет: обычное удаление
завершённого экземпляра/состояния должно работать.

Индексы: PK задания и уникальность копии/сессии/фактов — точные обращения;
частичный индекс задания с session_id IS NULL AND disposed_at IS NULL —
перечисление активных удерживаемых владельцев без истории. Нового TTL/worker нет.

## 2. Точные факты прежнего журнала

Три закрытых вида наблюдений в прежних ограниченных/хешированных фактах:

- `planning_db_retained`: точные job/task/attempt/clone, поколение, digest
  планирования/отпечаток исполнения, полные ID/имя runtime, operation_ref,
  target_path, управляемая идентичность и исходный kind/ID. Настоящие читающие
  проверки той же живой готовой БД/верифицированной операции после успешного
  завершения точного планировщика. Это **не** db_quiescence/runtime_absent.
- `planning_db_disposal_requested`: ссылка на удержание и неизменяемый план;
  одна причина/полномочие: source_mismatch, full_cache, accepted_cancel или
  selected_failure. Несовпадение источника содержит настоящий первый шаг/
  привязку/вход; полный кэш — настоящие завершённые кэшированные шаги/состояния;
  отмена/ошибка — прежнее сохранённое основание. Произвольной строки причины
  недостаточно. Пустой план не переходит в удержание.
- `planning_db_disposed`: точные факты удержания/запроса и свежее подтверждение
  отсутствия полного ID, retired управляемой операции и отсутствия закрытого
  рабочего каталога. Передачи/публикации в этой ветке нет.

Scope/поколение каждого факта совпадает с точной попыткой, digest канонический.
Прежние 8192 байта и append-only-защиты сохраняются. Настоящие наблюдения идут
до транзакции через доверенный проверяющий с типизированными ожидаемыми ID;
SQL повторно сверяет точного текущего владельца/идентичность. Флаг CLI/API не
заменяет физическое наблюдение.

## 3. Завершение планирования с живой БД

Новый узкий `CompleteRetainedPlanning` использует прежнее владение соединением/
сверку фиксации. Только обычный running prepare, непустой проверенный план,
успешный остановленный private/v2-планировщик, точный active preview и отсутствие
рабочей истории/отмены/конечного исхода допускают путь. Это уточнение штатного
пути принимает только попытку планирования 1, не восстановленную/повторённую
вторую попытку. Вывод и порядок фактов
точные: успешная executor_inspection < planning_db_retained < planning_output.
Сохранённые байты/digest плана соответствуют захвату.

Одна транзакция вставляет запись владения, complete_planning с ровно тремя
ссылками на эти факты, закрывает точную попытку как planning_result_saved и
завершает стабильное задание плана. Прежняя SQL-защита завершения получает
**отдельную точную альтернативу** доказательству отсутствия; прежняя ветка
отсутствия неизменна. Копия остаётся active с тем же ID; ложные db_quiescence
или released не записываются.

После ошибки/неясного COMMIT успех возможен только после полной сверки на
точном соединении: строка, факты/ссылки решения, план, попытка/задача, операция/
копия. Частичного перечитывания недостаточно. До транзакции прежняя активная
копия планирования защищает runtime, даже если план или факт уже сохранены.
Если отмена/ошибка выбрана раньше, удерживаемое завершение запрещено и БД
по-прежнему очищает исходный владелец планирования.

Закрытый вывод планировщика после этого можно очищать по plan_saved с отдельной
точной альтернативой удерживаемого владения вместо отсутствия БД. Прежние
наблюдения остановленного исполнителя/вывода/входа сохраняются. БД, источник,
каталог и операция защищены; ReleasePlanningClone запрещён при удержании или
передаче живой сессии.

## 4. Атомарная передача единственной первой сессии

Новый `TransferPlanningDBToFirstSession` — одна транзакция точного соединения,
без Docker/файлов. Требуются удержание без запроса очистки, точный исходник и
первый **некэшированный** настоящий running state_execute с привязкой; нет
прежней сессии/попытки применения, отмены/конечного исхода; точные завершённые
планирование/задача/вывод. Задание — running обычный prepare, не recovery_required,
plan-only или объяснение кэша.

1. Однократно связать будущие session_id, first_task_id, first_execution_digest
   и transferred_at с проверкой всего кортежа.
2. Вставить одну сессию planned runner с **существующей** active копией,
   теми же поколением/runtime/источником и начальным курсором. Прежние аренда
   помощника и настройки; без новой prepare_clones/повышения clone_generation
   только ради передачи владения.
3. Проверить связку строки/сессии/первой привязки/плана/копии/операции. Отложенный
   FK запрещает фиксацию без сессии; точные защиты обеих сторон не позволяют
   подставить другую сессию.

INSERT сессии с копией, когда-либо использованной попыткой планирования,
обязательно требует этой точной передачи в той же транзакции. Общая защита
совпадения источника не разрешает присвоить копию без записи владения, при
удержании или при ссылке на другую будущую сессию.

Только известный COMMIT/полная сверка разрешают передать runtime обычному
рабочему runner. Готовность и допуск первого вызова прежние и предшествуют SQL.
Вторая сессия или новая копия не подменяют неясную передачу. Старое доказательство
первой сессии при восстановлении сохраняет released-preview: его **не расширяют**
для запуска SQL по истории удержания.

Обычные курсор/снимки/успех/ошибка/отмена и передача экземпляру используют ту же
сессию/копию. После передачи новая строка — история. Планирование не может
забрать эту БД для очистки; перечисление владельцев учитывает одну физическую
копию, а не две аллокации по ссылкам планирования/сессии.

## 5. Отказ от переиспользования, удаление и границы сбоя

При кэшированном префиксе/другом источнике или полном кэше точный запрос очистки
фиксируется до разрушения. Передача и запрос очистки не могут оба зафиксироваться.
Затем владелец планирования завершает точную управляемую операцию, удаляет точные
БД/каталог, наблюдает отсутствие вне SQLite. Одна сверяемая транзакция связывает
факт/время удаления и освобождает копию. Только известное завершение разрешает
прежний запуск сессии из нужного нового источника.

После запроса очистки отмена/ошибка может выбрать конечный исход, но не очистить
запрос, перенаправить удаление или разрешить SQL. Очистка завершается по прежнему
точному основанию. Живая переданная сессия не попадает в эту ветку, даже если
позже обычным образом завершилась.

Удаление/конечный успех/ошибка задания запрещены при удерживаемом владельце или
незавершённой очистке и любых прежних живых сессиях/закрытых владельцах. Удаление/
вытеснение источника и изменение/retirement операции учитывают живую защиту.
Точный путь очистки завершает операцию лишь по зафиксированному совпадающему
запросу: исключение не позволяет менять Source, target или runtime.

Защиты эффектов/фактов финализации допускают после сохранённой отмены/ошибки
только точные запрос/завершение очистки уже удерживаемого владельца. Новое
удержание, передача, сессия и попытка применения после выбора исхода запрещены.
Общего разрешения всех новых видов наблюдений не допускается.

Переданная история не становится вечной защитой: после штатного завершения
сессии/передачи экземпляру/финализации обычное удаление экземпляра/состояния
работает. Прямое удаление истории/фактов/ссылок при существующем задании запрещено.
Каскад завершённого задания разрешён после удаления родительской строки;
защиты не зависят от порядка соседних каскадов FK.

Сбой до фиксации удержания — исходный preview-владелец; после — удерживаемый.
Неясная передача — после сверки один из владельцев планирования/сессии, без
предположительного SQL/очистки. После передачи — сессия. После запроса удаления —
незаконченная очистка планирования. После физического удаления до COMMIT —
всё ещё удерживаемый ожидающий очистки владелец, не источник для SQL.
Автоматического перезапуска/повтора/замены и общего восстановления не добавляется.

Точная проверка `operation.Source` и runtime ID повторяется при чтении
сохранённого владельца. Защита запроса очистки в SQL, как и писатель, требует
настоящего происхождения каждого кэшированного состояния/префикса, их точной
последовательности и сохранённых полномочий. Одни `cached`-флаги не дают права
удалить БД. Локальные CP-PG03 воспроизводят и блокируют оба прежних обхода.

## 6. Установка и ограниченная поверхность изменений

Версия компонента сессий **3 → 4**; общий attempts=3, привязка Liquibase=2,
завершение=2, выбор кэша=1 и протоколы манифестов прежние. Точный эталонный
каталог включает новую таблицу/индекс/защиты и адресные изменения планирования,
сессии, очистки, конечного статуса/удаления и перечня активных владельцев.
Общие psql-семантика и неизменяемость идентичности копии не меняются.

Новая установка и утверждённый переход с точной выпущенной схемы используют
конечные определения напрямую. Нет миграции с невыпущенного формата #89 версии
3, неявного ремонта или обновления его незавершённых заданий. Неизвестный/
частичный/изменённый каталог отвергается до записей/worker/probe. Исторические
хеши источника остаются историческими; целевые хеши/версии тестов меняются только
по утверждённым PG01–PG10 / OT-PG01; выпущенные хеши источника сохранены.

## 7. Критический и повторный разбор

Исправлено: живой preview нельзя объявлять отсутствующим/quiescent; передача не
фиксируется без точной сессии; ссылки плана/сессии не дают двух владельцев
удаления; несовместимый курсор и recovery_required не допускают запуск; намерение
удаления предшествует эффектам; сверка COMMIT удерживает соединение и весь
кортеж. Исторический FK операции навсегда закреплял бы удалённый экземпляр —
используются факты/ограниченные живые защиты. Проверка родительского задания
исключает уже наблюдавшийся отказ из-за порядка каскадов.

Повторный разбор проверил сочетания переходов, порядок отмены/ошибки, scope/
порядок фактов, поздние/неясные фиксации, защиту источника/пути, закрытую очистку,
обычное удаление опубликованного экземпляра и прежнюю выпущенную установку.
Открытых P0–P2 на уровне схемы не найдено. Тесты/точные правки старых ожиданий —
следующее отдельное утверждение, не подразумеваются этим предложением.
