# Аутентификация CLI

CLI использует серверный обмен токенов по [OpenAPI](../api-guides/sqlrs-engine.openapi.yaml).
Схема discovery версии 2 заменяет прежнюю схему внутри `/v1`. Согласования версий
и возврата к прямому обмену с провайдером нет. [Решение](../adr/2026-10-28-installation-token-exchange.md).

## Вход

1. `sqlrs auth login <provider>` выбирает удалённый профиль remoteSession и без
   авторизации получает описание провайдера. До открытия браузера проверяются
   идентификатор, адаптер, возможности, адреса и параметры входа. Адреса обмена
   и обновления должны принадлежать доверенному управляющему адресу инсталляции.
   Предварительное получение полного списка провайдеров не требуется.
2. CLI создаёт state, nonce и PKCE S256, запускает временный обработчик на
   `127.0.0.1` со случайным портом и собирает адрес входа из настроек провайдера.
   Параметры Google не добавляются по умолчанию.
3. Браузер проходит вход у провайдера. Код возвращается на
   `http://127.0.0.1:<port>/`; CLI проверяет state, issuer ответа и ошибки.
   С `--no-browser` адрес сразу выводится в stderr для ручного открытия.
4. CLI отправляет код, точный адрес возврата, проверочную строку PKCE, nonce и
   ожидаемые идентификаторы инсталляции, issuer и клиента на серверный метод
   `/v1/auth/providers/{provider}/exchange` без сохранённого bearer-токена.
5. Сервер проверяет выбранные настройки, обменивает код с собственными client ID
   и секретом, проверяет подпись ID-токена и синхронно возвращает токены с
   `Cache-Control: no-store`. Пользовательские сессии и токены на сервере не хранятся.
6. CLI самостоятельно проверяет issuer, единственный audience, необязательный
   azp, subject, nonce и срок действия, затем атомарно заменяет запись системного
   хранилища. Access token не заменяет ID token. При ошибке входа прежняя запись
   сохраняется. Секрет приложения в CLI не попадает.
7. После сохранения выполняется прежнее согласование профиля и адреса организации.
   Ошибки маршрутизации и доступа отделены от ошибки входа; новая сессия сохраняется.
   Подробности приведены в [руководстве](../user-guides/sqlrs-auth.md).

## Защищённые запросы и обновление

Явный `SQLRS_TOKEN` имеет наивысший приоритет. Иначе полная сессия находится по
профилю, постоянному идентификатору инсталляции и её нормализованному управляющему
адресу. Адрес организации в ключ не входит. Провайдер и учётная запись находятся
в значении записи. Неполные прежние записи требуют повторного входа.

Пригодный сохранённый ID-токен используется повторно. Для отсутствующего или
подлежащего обновлению токена CLI без авторизации получает актуальные настройки
провайдера и вызывает `/v1/auth/providers/{provider}/refresh`, передавая исходные
subject, nonce и ожидаемые параметры инсталляции. Изменение доверенных настроек
останавливает отправку refresh token. Браузер при обновлении не открывается.

Сервер использует собственный секрет и проверяет результат провайдера. CLI также
проверяет личность и срок действия до сохранения. Новый refresh token заменяет
старый; отсутствие нового сохраняет отправленный. Явно пустая замена недопустима.
Пятиминутное упреждение обновления не является минимальным сроком жизни токена.

Любой отказ обновления, включая invalid_grant, отмену, потерю ответа и ошибку
проверки, не удаляет, не записывает и не восстанавливает запись хранилища.
Параллельный процесс мог уже сохранить новый токен. Блокировки обновления и
гарантии единственного обмена нет. POST-запросы не следуют перенаправлениям и
не повторяются автоматически. Ответ ограничен 1 МиБ; действует таймаут команды,
по умолчанию 30 секунд.

## Состояние, выход и хранение

`sqlrs auth status` читает безопасные локальные сведения без обновления и проверки
отзыва токена. Он показывает наличие SQLRS_TOKEN, не раскрывая его значение.
`sqlrs auth logout [--no-revoke]` пытается выполнить объявленный отзыв без секрета,
если он не пропущен, затем удаляет локальную сессию даже при ошибке отзыва или
получения настроек. Переменная окружения остаётся нетронутой.

Токены сохраняются только в Windows Credential Manager, macOS Keychain или
Linux Secret Service/libsecret. Хранения в открытом файле нет. Имя записи Linux
и macOS совпадает для чтения и записи и не зависит от выбранного провайдера.
Токены, коды, проверочные строки и секреты не выводятся в обычные сообщения,
JSON-ошибки и диагностику.

## Добавление провайдера

Идентификатор провайдера выбирает экземпляр настроек, а `oidc` — адаптер протокола.
Совместимый экземпляр добавляется конфигурацией и перезапуском без пересборки CLI
и сервера. Нужны PKCE S256, локальный адрес возврата, iss в ответе, RS256/JWKS,
единственный audience, постоянный subject, refresh token и новый ID token при
обновлении. Определение организации остаётся отдельной задачей.
