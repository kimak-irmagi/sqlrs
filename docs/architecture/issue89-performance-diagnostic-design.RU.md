## Вопрос и выбранная граница

Полные короткие серии доказывают замедление v2, но содержат итоговое время,
не длительность операций. Дополнительная проверка образа/планирование — гипотеза,
не измеренная причина. Начать с диагностического JHipster на стандартной Ubuntu
Actions, наблюдая **те же точные бинарники v1/v2**, без новых границ продукта/API/БД.

Использовать внешние отметки запусков/завершения процессов `strace` и отдельные
существующие отметки журнала SQLite. [Руководство strace](https://man7.org/linux/man-pages/man1/strace.1.html)
описывает наблюдение дочерних процессов, времени и выходов без пересборки программы.
Не подменять Docker обёрткой: это меняет поведение дочерних процессов/сигналов.
Не записывать содержимое read/write и не присоединяться к чужим процессам.

## Компоненты, взаимодействие и владение

1. Отдельный процесс Actions с явной меткой PR своего репозитория
   `performance:diagnostic`: новая Ubuntu 24.04, токен только чтения, отдельная
   группа одновременных запусков. Без платных машин, ноутбука, отмены полного
   прогона и запуска при обычном push. Одно задание, предел 60 минут с более ранней
   границей для уборки.
2. Получить закреплённый измеряемый `668d505` в корень рабочего каталога,
   точную ревизию диагностических средств — в игнорируемый дочерний `.tmp`.
   Прежняя процедура подготовки/прогрева работает с закреплёнными исходниками;
   утверждённое ниже уточнение разрешает скрипт подготовки из checkout наблюдателя
   с явным корнем первого checkout. Обязателен
   SHA256 кандидата `1367bce9ddaa44c0aa378b07c015dfb20a4c0d29f00d2f5a893905686fae14b0`
   и прежний закреплённый хеш v1. Наблюдатель собирается отдельно; заменяется
   только его закрытый тестовый бинарник. Измеряемые исходники/бинарники не меняются.
   Аудит выявил хеш `liquibase.bat` у исходного наблюдателя Linux v1 при реальном
   запуске `liquibase`. Диагностика обязана использовать фактический выбранный
   скрипт, сверенный с закреплённой извлечённой поставкой; не называть его хешем
   Windows-скрипта. Прежние выборки не переписываются; производные числа JVM
   предварительны до проверки настоящего скрипта. Правка наблюдателя получит
   отдельные проверки.
3. Только внешний сборщик получает явный диагностический режим. В нём точный
   движок запускается под `strace`, в обычном — без изменений. Оба остаются
   в принадлежащей тесту группе процессов. Сохраняются API, полные эталоны БД/кэша,
   события, завершение и точная уборка. Прежний путь без трассировки — по умолчанию;
   старые утверждения не ослабляются.
   В режиме трассировки PID запуска принадлежит strace: перед доверием адресу/
   токену независимо проверить, что опубликованный PID движка — его живой прямой
   потомок в той же своей группе, исполняющий точный выбранный бинарник. В обычном
   режиме сохранить прежнее равенство PID. Для подготовки теста потребуется
   отдельное адресное согласование; просто убирать проверку владения нельзя.
4. Две обычные пары v1/v2 и две пары с трассировкой, во второй паре каждого вида
   порядок обратный. Каждый запуск — новое хранилище и затем кэшированный проход.
   Сравнивать одинаковые режимы, стоимость наблюдения сообщать отдельно. Это
   локализация, не приёмочная серия и не разрешение менять/отменять P01b.
5. Только exec/завершение процессов с отметками времени. Закрытые файлы 0600
   под точным корнем сборщика с признаком владельца, предел 32 МиБ и фиксированные
   ограничения строк/длины. Читать трассу через отдельный канал и ограниченный
   писатель, не периодически проверяемый неограниченный файл; при завершении
   дождаться читателя. При переполнении/сроке завершать свою группу. Аргументы
   могут содержать пароли/SQL: не печатать и не публиковать трассы, потоки, БД/настройки.
6. Чистые обычные помощники Go разбирают ограниченную трассу, связывают успешный
   exec с завершением по PID, отвергают обрезанные/неоднозначные данные. Наружу —
   закрытые категории: Docker inspect/create/start/stop/remove/copy, проверка
   образа, вызов планировщика/шага, управление/проверка PostgreSQL, Liquibase
   на хосте, Java на хосте, прочее. Без исходных аргументов, путей, ID и сообщений.
   Повторный успешный exec того же PID закрывает предыдущий участок исполнения;
   ошибочная попытка exec не считается успешным запуском. Время самого движка
   исключается из расходов дочерних команд. JVM внутри контейнера хостовая трасса
   не видит: наблюдается синхронный интервал Docker exec, не вымышленные процессы JVM.
7. Вне измеряемых интервалов читать только разрешённые отметки/порядковые номера
   из существующего журнала заданий/шагов/планирования/сессий/вызовов. Не выгружать
   SQL, request_json, сообщения событий, DSN и идентификаторы экземпляров. Выдавать
   крупные фазы задания и номера шагов относительно запроса; недоступные в версии
   границы отмечать как отсутствующие, не как нулевое время.
8. Диагностический запуск проверяет бинарники и обычный результат нагрузки,
   публикует только типизированный числовой/категориальный JSON отдельного каталога.
   Указать идентичность трассировки/исходников/версий, проход/режим, время API,
   интервалы/числа процессов и фазы журнала. Вложенные интервалы разделяются:
   нельзя складывать пересекающиеся операции как независимое время. Показывать
   непокрытое/остаточное время; необъяснённый остаток не выдаётся за найденную причину.

Сборщик дожидается завершения движка/дерева перед итоговым разбором трассы,
затем удаляет закрытые файлы прежним точным протоколом. Выход strace не доказывает
выхода движка. Ошибка наблюдения/разбора/уборки, обратный ход времени, несвязанный
завершённый вызов или противоречие счётчикам оставляют диагностику неполной.
Жёсткое завершение машины не означает успешную уборку.

Если найдена только крупная фаза (например привязка/сеть или SQLite), явно
сообщить предел знания и предложить следующее узкое наблюдение, а не точную
причину по чтению исходников. Продуктовое исправление предлагается отдельно,
с проверками требований до реализации.

## Критический и повторный разбор

- P1: наблюдатель незаметно меняет кандидата. Обязательны закреплённые исходники
  и оба настоящих хеша; сборка/данные наблюдателя принадлежат отдельной границе.
- P1: утечка или подмена приёмки трассировкой. Только закрытый набор разобранных
  данных; ограниченные закрытые файлы; диагностика не смешивается с P01b.
- P1: выход strace при живом движке. Сохраняются и проверяются владение группой
  и точная очистка; нет флагов фонового отделения трассировщика.
- P1: прежняя проверка PID принимает чужой сервис или отвергает настоящего
  потомка strace. Отдельное доказательство /proc потомка/группы/бинарника для
  трассировки; прежнее равенство для обычного пути не меняется.
- P1: двойной учёт вложенных Java/shell/Docker. Сохраняются интервалы и объединение
  их покрытия, не фиктивная сумма независимых затрат или ненаблюдаемое родство.
- P2: отсутствие/отказ наблюдения выглядит нулевыми расходами. Ограниченный разбор,
  сверка номеров/счётчиков и явная неполнота/остаток.

Повторный разбор не выявил оставшихся P0–P2 этой границы компонентов. Изменение
старых тестов самим проектом не разрешено. Рассмотренный отдельный перечень
и три точные правки сборщика впоследствии утверждены отдельно.

2026-11-09: повтор `42612253733` снова завершился на запуске 3 с `trace_5`.
Попытка exec началась не позже конца последнего окна API, поэтому узкое
исключение поздней уборки правильно не сработало. Из этого ещё не следует,

Утверждён явный режим только измеряемого декодирования:

- При уже прочитанном начале exec и точной конечной записи того же процесса,
  но без результата exec, сохранять интервал **exec.unconfirmed** от начала
  попытки до конечной записи. Ни имени программы, ни PID/аргументов в отчёте нет.
  Прежний подтверждённый образ заканчивается у начала этой попытки: его работу
  нельзя приписывать всему неясному интервалу.
- Этот интервал не означает успешный запуск CLI/JVM. Счётчики успешных CLI,
  эталоны БД/кэша и уборка проверяются прежним независимым путём. `Commands`
  остаётся числом показанных интервалов, а не количеством успешных CLI; отдельная
  категория явно сохраняет неопределённость, не прячет её в Java/Docker.
- Строгий декодер по умолчанию и прежние отрицательные тесты сохраняются.
  Повреждённый/обрезанный поток, отсутствие конечной записи, несвязанные PID,
  обратное время и неподтверждённая уборка по-прежнему означают отказ. Новый режим
  не даёт права пропускать строки или считать EOF доказательством выхода.
- Значимая необъяснённая стоимость этих интервалов остаётся ограничением анализа:
  нельзя объявлять её конкретной причиной замедления. Продукт/API/БД/полномочия
  повтора SQL не меняются; новых точек чтения и сырых данных в отчёте нет.

Альтернатива — сохранить полный отказ при такой форме записи и отдельно
спроектировать другой способ наблюдения. Рекомендуется отдельный неясный
интервал: наблюдатель честно различает известное время и неизвестный результат.
Критический разбор закрыл P1 ложного успеха/атрибуции и P1 пропуска повреждённого
потока перечисленными ограничениями; повторный разбор новых P0–P2 не выявил.
Решение принято; отдельный перечень EU01–EU06 приведён в
[проверках диагностики](issue89-performance-diagnostic-tests.RU.md#на-согласование-eu01eu06-неподтверждённый-exec).
Явный режим реализован в наблюдателе; прежние строгие вызовы/тесты не менялись.

## Утверждено: закрытый контекст нераспознанной записи

Статус: явно утверждено @evilguest 2026-11-09; точное время ответа недоступно.
Отдельный перечень CX01–CX05 затем утверждён до тестов/реализации. Контекст проходит
малые регрессии/vet; настоящий CX05 ещё не завершён.

Запуск `42618850460` на наблюдателе `a75316b` прошёл подготовку, настоящий smoke
и два обычных запуска, затем остановился на v1 под strace с `trace_8`. Этот код
сейчас означает либо нераспознанную отдельную запись, либо неверное начало
pending при обработке выхода. Байты трассы в артефакте не сохраняются; сам код
не устанавливает ни форму записи, ни причину в продукте.

Утверждены метаданные только отказа из той же уже прочитанной закрытой записи:

- Закрытый перечень места отказа: `record`, `pending_entry` или `none`.
- Закрытый перечень формы: `superseded_exec`, `exec_entry`, `exec_resume`, `other`
  или `none`. Узнавать только фиксированные начала/формы с якорем, включая
  числовую форму отметки superseded exec; её PID, текст и аргументы не выдавать.
  `other` — ограничение знания, не разрешение пропустить запись.
- Сохранить прежний код ошибки и строгий отказ. Также сохранять уже выдаваемый
  закрытый `P01B_FAILURE_STAGE` с тем же перечнем этапов, что у обычного отчёта
  серий: ошибка разбора при уборке не должна скрывать фазу первичного отказа.
  Отсутствующий/чужой этап становится `collector_exit`. Этап — последняя
  достигнутая фаза; сам по себе он не устанавливает первичную ошибку нагрузки
  (отказ уборки возможен и после успешной нагрузки).
- Нет допуска нового синтаксиса strace, новой границы чтения/вывода сырых данных,
  изменения системных вызовов, продукта или протокола восьми запусков. Следующее
  изменение декодера должно обосновываться полученными данными, не этой гипотезой.

Альтернативы: повторять без новых сведений; выдавать очищенную исходную строку
(отклонено из-за возможных закрытых аргументов); либо выдавать только фиксированный
контекст. Рекомендуется последнее. Критический разбор: P1 утечка подстроки —
формировать только фиксированные значения; P1 метка формы принята за допустимую
запись — отказ сохраняется; P2 уборка скрывает ранний отказ — отдельно сохранять
прежний этап. Повторный разбор оставшихся P0–P2 не выявил. Проект и отдельно рассмотренный

## Утверждено: неизвестные вызовы и время процесса без установленной программы

Статус: явно утверждено @evilguest 2026-11-10; точное время ответа недоступно.
Отдельный перечень UR01–UR07 затем утверждён до тестов/кода. Пользователь отдельно
разрешил точную правку границы UR01. Полные малые Go/Node и Linux vet теперь
проходят; настоящие UR06/UR07 ещё открыты.

В [исходниках strace 6.8](https://github.com/strace/strace/blob/v6.8/src/syscall.c#L1309)
есть явная обработка неизвестных вызовов: сырые аргументы, числовое имя при наличии
номера и исходные признаки трассировки. Поэтому выбор execve/execveat не позволяет
считать любую unfinished-запись началом exec. Это обосновывает отдельную грамматику
наблюдателя, а не точную причину исходного замедления. Удалённый отчёт устанавливает
семейство, но не числовые данные и не точную версию запущенного strace; по эталонному
исходнику нельзя приписывать эти значения настоящему запуску.
См. также [признаки сырых аргументов/трассировки](https://github.com/strace/strace/blob/v6.8/src/defs.h#L345).

Утверждено дополнение только измеряемого режима; строгий режим сохраняется:

1. Отдельный ограниченный разбор точных форм неизвестного вызова (`syscall_0x…`
   либо `???`), только числовые сырые аргументы, без строк по указателям. Точную
   грамматику Linux/amd64 задать в отдельно рассмотренном перечне тестов до кода.
   Охватить начало, совпадающий resumed, явный результат и форму без результата/
   с конечной записью; проверять всю запись, не метку начала. Несовпадение имени/
   PID, повреждения, обратное время и отсутствие нужного завершения остаются
   отказами. Произвольные имена вызовов и пропуск строк не разрешаются.
2. Допустимый неизвестный вызов не устанавливает программу или успешный exec.
   Прежний подтверждённый образ закончить у начала неизвестного вызова; далее
   сохранять **process.unattributed** до следующего подтверждённого образа либо
   точного выхода того же PID. Не восстанавливать прежнюю категорию по неизвестному
   результату и не приписывать время Java/Docker. Для pending нужен совпадающий
   результат либо точная конечная запись; EOF не подтверждает отсутствие процесса.
   Время самого движка исключено. Прежние окна API/объединение без двойного учёта.
3. Категория означает время процесса без установленной программы, не длительность
   системного вызова и не успешный CLI/JVM. Commands остаётся числом интервалов.
   Прежние независимые счётчики, эталоны БД/кэша и очистка обязательны. Значимое
   нераспределённое время ограничивает локализацию, не становится заявленной
   причиной продукта. В Node добавить только фиксированную категорию; номер
   вызова, аргументы, PID и исходный текст не выдаются.
4. Прежние строгие отказы и неверные/неполные записи PX02 с их точными
   кодами сохранить. Измеряемый путь получает только полностью проверенная
   грамматика; метки структуры не разрешают вход. Нет изменений продукта/API/БД,
   новых данных/флагов трассировки или нового протокола восьми запусков. До него —
   дополнительная малая настоящая проверка неизвестного числового вызова в Actions
   на том же Ubuntu/strace; без БД/Liquibase и нагрузки ноутбука.

Альтернативы: сохранить полный отказ наблюдателя; отбрасывать неизвестные записи
(отклонено, поскольку скрывает неопределённость); либо разбирать их ограниченную
грамматику и сохранять время явно без установленной программы. Рекомендуется
последнее. Критический разбор: P1 допуск по одному началу — проверять всю грамматику;
P1 ложная программа — отдельная категория/ранняя граница прежнего образа;
P1 успех без выхода — точные проверки жизненного цикла; P2 ослабление старых
тестов — строгий режим/неверные подготовки сохраняются; P2 зелёный наблюдатель
подменяет приёмку — P01b сохранён. Повторный разбор оставшихся P0–P2 не выявил.
Дополнение компонентов и отдельно рассмотренный
[перечень UR01–UR07](issue89-performance-diagnostic-tests.RU.md#на-согласование-ur01ur07-грамматика-неизвестных-вызовов-и-нераспределённое-время)
утверждены. Локальная реализация сохраняет строгий разбор; UR06 и восемь
удалённых запусков с ней ещё не начаты. См. отметку в перечне тестов.
