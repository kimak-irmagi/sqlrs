# Runtime v2: публичные типы и устройство схемы среды выполнения

Статус: **API и структура компонентов утверждены** @evilguest 16 октября
2026 года, #150, после исправлений и повторного разбора, включая уточнённую
[границу взаимодействий](runtime-v2-execution-schema-flow.RU.md). Перечень
тестов отдельно утверждён 16 октября 2026 года. Реализация и тесты представлены в
[PR #152](https://github.com/kimak-irmagi/sqlrs/pull/152); итоговая приёмка по ревью
и CI относится к его последнему коммиту. Неизменяемый выпуск v0.6.0 завершён в
[#151](https://github.com/kimak-irmagi/sqlrs/issues/151). Утверждённая функция
[преобразования произвольной командой](runtime-v2-execution-transform.RU.md)
#156 связывает прежнюю идентичность выполнения; её реализация и выпуск отдельны.

## 1. Ответственность и объём

Меняется только существующий модуль `backend/libs/runtime-go` со стандартной
библиотекой. Не добавляются службы, CLI, HTTP API, база или исполнитель.

| Файл | Ответственность |
| --- | --- |
| Корневой `canonical_value_inspect_v1.go` | Чтение дерева через существующий разбор канонических значений. |
| `schemas/sqlrs/execution.go` | Значимые типы, получение схемы, атомарные Build/Parse. |
| `schemas/sqlrs/execution_validation.go` | Общие проверки формы, имён, путей, ссылок и размеров. |
| `schemas/sqlrs/execution_value.go` | Перевод типов в публичные канонические деревья и обратно; без своего кодировщика или хеширования. |

Зависимости — корневые публичные типы и внутренний импорт `schemaauthor`,
не `resolver`, Docker или файловая система. Поставщики отвечают за доказательства
содержимого, обработку исходных описаний, привязку физических путей, проверку
возможностей и запуск. Схема описывает один запуск, но не требует нового процесса
на каждой внутренней границе прогресса. Неизвестные настройки, влияющие
на поведение, нужно представить или отклонить, а не потерять незаметно.

## 2. Публичный интерфейс

```go
func ExecutionEnvironmentSchema() runtimev2.ExtensionIdentitySchema
func BuildExecutionEnvironmentIdentity(ExecutionEnvironmentInput) (
    runtimev2.CanonicalResolvedExtensionIdentity, error)
func ParseExecutionEnvironmentIdentity(runtimev2.CanonicalResolvedExtensionIdentity) (
    ExecutionEnvironmentInput, error)
```

Точные объявления Go зафиксированы в [английском разделе API](runtime-v2-execution-schema-structure.md#2-exact-constructionread-api).
Содержание типов:

| Тип | Поля |
| --- | --- |
| ExecutionEnvironmentInput | Runtime, Argv, Environment, Workdir, User, Network, Inputs, Mounts, Services, Secrets |
| ExecutionRuntime | Kind, IdentityKind, IdentityDigest, Platform, DatabaseService |
| ExecutionPlatform | OS, Architecture, Variant |
| ExecutionPath | Root, Relative |
| ExecutionText | Список ExecutionTextPart |
| ExecutionTextPart | Kind и только соответствующие ему Literal; SecretSlot; ServiceRole/ServiceField; либо Path/PathFormat |
| ExecutionEnvironmentVariable | Name и Value типа ExecutionText |
| ExecutionInputBinding | Name, Source, Profile, Executable |
| ExecutionInputReference | Provider, Kind, IdentitySchema и Fingerprint типа CanonicalFingerprint |
| ExecutionMount | Name, InputName, Target типа ExecutionPath, Kind, SecretSlot, ReadOnly |
| ExecutionServiceBinding | Role, Protocol, Database, User, Transport, AuthenticationSecret, AuthenticationProfile |
| ExecutionSecretBinding | Name, Purpose, ServiceRole, необязательный IdentityReference типа *SecretReference |

Это входные и читаемые представления, не второй результат или идентичность.
Build атомарно возвращает существующий канонический тип; Parse проверяет
и читает его. Нет изменяемого объекта построения, общего определения схем,
нового формата передачи или вспомогательного интерфейса наблюдений.

Перечисления — отдельные строковые типы. Точные имена констант даны рядом
с объявлениями Go. Их замкнутые значения:

| Тип | Значения |
| --- | --- |
| ExecutionRuntimeKind | host, oci, database-container |
| ExecutionRuntimeIdentityKind | image-manifest, host-bundle, host-executable |
| ExecutionTextPartKind | literal, secret, service, path |
| ExecutionPathFormat | native, forward-slash |
| ExecutionMountKind | input, scratch, secret |
| ExecutionInputProfile | regular-file.v1, regular-tree.v1 |
| ExecutionSecretPurpose | authentication, semantic |
| ExecutionServiceTransport | tcp, unix-socket |
| ExecutionNetworkMode | none, services, local-context |
| ExecutionServiceField | host, port, database, user |

Нулевое и неизвестное значение отклоняются. Схема не определяется заново
для каждого вызова.

## 3. Разрешённая команда вместо исходных настроек

Build получает итоговые аргументы, среду, каталог и пользователя. В нём больше
нет флагов наследования/очистки, указателей на списки команд и режима image/replace.
Эти различия сохраняются на стадии объявления и разрешения. Поставщик читает
ограниченную проверенную конфигурацию образа и применяет правила источника
до Build, без загрузки слоёв и запуска инструментов.

Для Compose совместно применяются [правила entrypoint](https://docs.docker.com/reference/compose-file/services/#entrypoint)
и [переменных среды](https://docs.docker.com/reference/compose-file/services/#environment):
явный entrypoint отключает стандартный CMD, если проектная command не задаёт
аргументы явно. Удалённой переменной нет в итоговой среде, пустая присутствует
с пустым значением. Исполняемая команда и аргументы образуют один список Argv.
Build не разбивает строки, не добавляет оболочку и не раскрывает переменные.

Различия отсутствия и пустоты важны при разрешении исходного описания, но
одинаковая итоговая конфигурация получает одинаковую идентичность. Прочитанный
объект не может заново запросить изменяемые значения по умолчанию через nil.
Workdir явный. User — выбранная учётная запись; для образа пустая строка означает
стандартную учётную запись платформы, не наследование от изменённого контейнера.
Для хоста фиксируется действующая учётная запись (UID, имя или SID), а не
разрешение сменить пользователя. Недоказуемое соответствие отклоняет поставщик.

Argv непустой. Первое слово — непустой литерал либо одна часть-путь, не секрет
или поле службы. Для хоста требуется путь с корнем tool и форматом native:
запускается именно проверенный инструмент. Остальной порядок сохраняется.
Соседние литералы сливаются, лишние пустые удаляются; полностью пустой аргумент
сохраняется одним пустым литералом. Литералы никогда не сканируются ради поиска
путей, оболочки или неявных подстановок.

Для полных профилей Environment — полная разрешённая значимая среда.
Значения из образа тоже классифицируются до Build: известный секрет нельзя
копировать как литерал только потому, что он пришёл из конфигурации образа.
Дополнительно видимы процессу только переменные, предписанные принятым профилем
аутентификации (§6), без конфликта с явными именами. Нельзя незаметно добавить
или изменить LANG, TZ, параметры JVM и другие входы под видом технической
подстановки. Для host-executable действует отдельное ограничение §7.

## 4. Пути и именованные входы

Путь — типизированная координата, не физическая строка хоста:

- mount:<name> — видимая точка именованного подключения;
- tool — проверенный локальный исполняемый файл (Relative только пустой)
  либо каталог полного инструментария; недоступен для профилей образа;
- workspace — локальный рабочий каталог, принадлежащий попытке;
- image — файловая система POSIX-образа; для Windows — image:<буква диска
  в нижнем регистре>, например image:c;
- service:<role>:socket, service:<role>:socket-directory и
  service:<role>:credential-file — файлы подключения, определяемые владельцем.
  Relative пустой; нужна существующая роль и соответственно unix-socket
  либо принятый профиль аутентификации, создающий файл.

Relative пустой либо чистый относительный путь с разделителем /: без начального,
конечного или повторяющегося разделителя, обратной косой черты, NUL,
компонентов "." и "..". Это логическая координата, независимая от хранения
рабочего каталога в Windows/Unix. Библиотека проверяет корни и ссылки.
Заведомо файловые и служебные секретные корни не могут быть рабочим каталогом
или точкой назначения подключения. Поставщик проверяет дополнительные совпадения путей на целевой файловой системе,
выход за разрешённый каталог, ссылки и реальные права: строка не даёт полномочий.

У части path заполнены только Path/PathFormat. Native даёт путь целевой
платформы; forward-slash — прямые косые черты, с префиксом диска для Windows.
Формирование происходит при выполнении после физической привязки, не при
расчёте идентичности. Workdir и точки подключения — такие же координаты,
не строки для неявного переписывания. Workdir должен быть каталогом:
заведомо файловый корень отклоняется без ввода-вывода, тип элемента дерева
проверяет владелец входа.

Пример одного слова: литерал --changelog-file= и путь
{Root: mount:project, Relative: changelog.xml}. Один исполнитель подставит
локальный временный каталог, другой — точку подключения контейнера.
Произвольные аргументы не подвергаются поиску и замене.

Именованный вход ссылается на существующую каноническую идентичность источника:
поставщик, вид, версия схемы и публичный хеш. Это ссылка, не полное описание
или доказательство. До использования поставщик проверяет полную идентичность
и право доступа. Библиотека проверяет запись ссылки, не наличие источника
или смысл схемы другого поставщика.

Правила материализации явно определяют наблюдаемые файлы:

- regular-file.v1 — точные байты обычного файла; Executable выбирает
  нормализованный режим 0755 или 0644. Время, владельцы и пути хоста
  не наследуются.
- regular-tree.v1 — полное версионированное описание дерева: относительные
  имена, виды каталог/файл, неизменяемое содержимое каждого файла и признак
  выполнения, включая пустые каталоги. Executable для всего дерева — false.
  Обычного нетипизированного хеша байтов каталога недостаточно.
- Оба профиля используют время эпохи, каталоги 0755, только обычные файлы,
  без ссылок, специальных файлов и дополнительных атрибутов. Владение задаётся
  учётной записью выполнения из разрешённого контекста. Права файла задаются
  до политики доступа подключения. Изменение профиля влияет на идентичность.
  Для записи создаётся отдельная копия или слой, не меняющий неизменяемый вход.

Формат описания источника и его проверка принадлежат указанной схеме источника.
Идентичность файла может представлять дерево только как версионированное
описание, понятое принятым поставщиком материализации; произвольный хеш нельзя
переименовать в дерево. #150 не реализует новый алгоритм хеша, поставщик дерева
или получение файлов. Нет совместимого владельца источника — запуск отклоняется,
а требование полноты не ослабляется.

## 5. Подключения, службы и политика сети

Имена подключений и входов уникальны. Input требует InputName без SecretSlot;
scratch не содержит обоих; secret требует значимого секрета, без InputName,
только чтение. Scratch допускает запись. Target привязан к image для образа
или workspace для хоста, не к другому подключению, службе или tool:
циклы в описании точки назначения невозможны.

Mounts — **упорядоченный список**, не словарь. Вложенные подключения разрешено
описывать: порядок применения влияет на идентичность, как в
[правилах OCI](https://github.com/opencontainers/runtime-spec/blob/main/config.md#mounts).
Адаптер определяет эффективный порядок до Build. Одинаковые логические точки
запрещены; дополнительные физические совпадения и неподдержанные перекрытия
проверяет поставщик. Ссылка mount видит итоговое пространство после перекрытий,
а не обещает, что затенённый файл всё ещё принадлежит родительскому входу.
Все слои остаются учтены.

Службы — логические цели, не переданные клиентом адреса. Явно задаются транспорт
TCP/Unix-сокет, протокол, база и логический пользователь. Подстановка
database/user требует непустого значения. Host/port требуют TCP, корни сокетов —
Unix-сокет. Для database-container обязательна ссылка DatabaseService;
в остальных случаях она пустая.

Сетевая политика не определяет наличие цели. None требует отсутствия сетевых
подключений; локальные сокеты и петлевой интерфейс дополнительно проверяются
поставщиком. Services ограничивает связи объявленными целями. Схема не запрещает
саму цель database-container или Unix-сокет при none. Поставщик доказывает
возможность сочетания транспорта и изоляции либо отклоняет его до изменений,
не ослабляя изоляцию незаметно.

Local-context допускается только для host-executable: явно используется
сетевой контекст разрешённого локального процесса, без обещания изоляции
или полноты зависимостей. Общие/полные профили это значение отклоняют.
Обычная локальная сборка может использовать сеть, но не становится изолированной
или пригодной для повторного использования; запреты §7 сохраняются.

Библиотека проверяет непротиворечивость описания, не обещает поддержку каждого
описания конкретным исполнителем. Привилегии, файловые системы, сеть
и поддержка инструментов остаются предметом допуска с объяснимыми причинами.

## 6. Назначение секретов и ограниченная аутентификация

Отсутствие ссылки не доказывает незначимость:

- Semantic требует действующую несекретную ссылку на неизменяемую версию.
  Неизвестное назначение, нулевые ссылки и значимые секреты без версии
  отклоняются Build и Parse, не становятся аутентификацией автоматически.
- Authentication требует ServiceRole без IdentityReference. Служба ссылается
  обратно через AuthenticationSecret, имеет непустого логического пользователя
  и версионированный AuthenticationProfile. Слот принадлежит одной службе.
  Это доступ под той же ролью, не произвольный секретный вход. Такой слот нельзя
  использовать в обычном тексте или подключении секретного файла.
- Принятый профиль аутентификации задаёт безопасную передачу через среду/файл,
  не меняет значимые параметры сеанса, пользователя, явные argv/env/пути.
  Неизвестный профиль, конфликт подстановок или невозможность обеспечить
  это свойство отклоняют запуск. Значения секретов, DSN и права доступа
  не попадают в идентичность, объяснение, аргументы или журналы.
- Части semantic secret разрешены в значениях среды, но не Argv. Значимые
  секретные файлы доставляет владелец; аргумент может ссылаться на их
  типизированный путь, но не раскрывать содержимое. Передача остаётся
  внутри границы владельца.

Классификация остаётся обязанностью автора/поставщика: произвольная программа
может намеренно использовать пароль как данные. Тогда он значим и требует
версии. Если это нельзя установить, выполнение с повторно используемым
состоянием не допускается. Эвристики по названиям и доказательства поведения
произвольной программы библиотека не обещает.

Службы, секреты и входы должны использоваться через цель, путь, подключение
или связь аутентификации. Повторы и неверные ссылки отклоняются.
Неиспользуемые данные происхождения не добавляются в идентичность.
Разрешённая цель сетевой политики тоже считается использованием службы:
необязательно повторять её в шаблоне, если её выбирает принятый файл проекта.

## 7. Локальный профиль и обязательный запрет повторного использования

Способы выполнения: host/oci/database-container. IdentityDigest — sha256
в нижнем регистре. Образ требует image-manifest: платформенный манифест,
не индекс или локальный номер. Для хоста есть два варианта:

- host-bundle: проверенный неизменяемый инструментарий с зависимостями
  и разрешённым контекстом процесса. Возможность общего запуска
  и повторного использования всё равно проверяется отдельно.
- host-executable: проверен только выбранный исполняемый файл. Обычный
  локально установленный инструмент допустим без заявления о неизменяемости
  всех внешних библиотек, PATH и системных служб.

Второй вариант привязывается к текущему локальному контексту вне канонического
объекта. Environment содержит только явные переопределения; User — текущая
учётная запись, Workdir — координата рабочего каталога. Перед стартом владелец
заново проверяет файл инструмента и контекст. Физический CWD, унаследованная
среда с возможными секретами, номера хоста и ссылки контекста не сохраняются.

**Обязательное правило:** успешный Parse не разрешает повторный запуск
на другом поставщике или использование готового состояния. Host-executable —
только локальное выполнение заново на каждый запрос, без выбора готового
State, публикации повторно используемого State или общего воспроизведения,
даже на том же хосте. Хранение результатов определения ресурсов не равно
хранению готовых состояний и не отменяет этот запрет. Он следует из
значения IdentityKind и не переопределяется наблюдением о переносимости.

Владелец проверяет это **до поиска или выбора готового состояния**, затем
повторно перед публикацией и общим воспроизведением. Ограничение сохраняется
от источника по всей цепочке: последующий полный профиль не делает потомка
неполного результата пригодным для повторного использования. Новую допустимую
основу даёт только заново проверенный полный источник, восстановление или
фабрика. Признак сохраняется в долговечных данных окружения и попытки после
сбоя. Один StateID или корректная цепочка не доказывают допустимость. Чистый
конструктор фиксирует профиль, но не управляет этим жизненным циклом.
Потребители реализуют ограничения до включения профиля в рабочем пути.

Идентичность честно фиксирует выбранный ресурс и объём описания, не неизвестные
зависимости. Это не доказательство воспроизводимости полного результата.
Для database-container владелец дополнительно проверяет, что файлы инструмента
соответствуют образу; отметка «локально» не оправдывает ложное утверждение.

ОС/архитектура — обязательные строки вида [a-z0-9][a-z0-9._-]{0,63},
вариант пустой либо того же вида. Нет фиксированной версии СУБД,
репозитория или неявного выбора платформы. Неподдерживаемую ОС нельзя
исправлять переосмыслением её идентичности.

## 8. Поля схемы, нормальная форма и чтение дерева

Поставщик sqlrs.execution, вид environment, схема sqlrs.execution-environment.v1.
Это утверждённая, но неопубликованная схема, не миграция прежних записей v1.

| Обязательное поле | Вид / раскрытие | Содержание |
| --- | --- | --- |
| primitive | text / public | Способ выполнения |
| runtime | canonical-value / protected | identity_kind, digest, platform (os/architecture/variant); database_service только для контейнера базы |
| invocation | canonical-value / protected | argv, environment, workdir, user |
| inputs | canonical-value / protected | Имя -> source (provider/kind/identity_schema/fingerprint), profile, executable (yes/no только для файла) |
| network | canonical-value / protected | mode и services (protocol, database, user, transport; authentication_secret/authentication_profile присутствуют вместе при аутентификации) |
| mounts | canonical-value / protected | Упорядоченные словари name, target, kind, access; input_name для input либо secret_slot для secret |
| secrets | canonical-value / protected | Имя -> purpose и service_role для authentication либо reference (provider/identifier/version) для semantic |

Путь — словарь root/relative. Части текста имеют kind и только соответствующие
ему literal; slot; role/field; либо path/format. Argv и части слов — списки.
Именованные коллекции — словари, nil и пустота нормализуются в пустой словарь.
Пути и строки не бывают null. Executable кодируется строкой yes/no,
поскольку canonical-v1 не имеет булевого узла; для дерева поле отсутствует.
Access — read-only/read-write. Формы узлов и варианты замкнуты:
лишние/отсутствующие ключи и неизвестные виды отклоняются.
Неприменимые поля Go тоже должны быть нулевыми/nil, а не теряться молча:
например ServiceRole у semantic, IdentityReference у authentication,
Literal/SecretSlot у части path. Режим подключения соответствует ReadOnly;
правила применимости file/tree проверяются до построения.

Имена переменных соответствуют [A-Za-z_][A-Za-z0-9_]{0,127}; для Windows
нормализуются в ASCII-верхний регистр до проверки повторов, иначе регистр
сохраняется. Имена связей — [a-z][a-z0-9._-]{0,63}. Протоколы, профили и схемы
используют существующие правила идентификаторов; AuthenticationProfile также
требует суффикс .vN с ненулевой версией. Текст — ограниченный UTF-8 без NUL.
Нет удаления пробелов или нормализации Unicode.

Коллекция несекретных ссылок — защищённый канонический словарь, создаваемый
и читаемый только через проверенные SecretReference. Кодирование одиночной
ссылки, типы узлов и области хеширования не меняются. В семипольной схеме
нет диагностических полей и конструктора наблюдений.

Parse проверяет поставщика, вид, схему, типы/раскрытие полей, суммарные размеры
и вложенную форму. Затем применяет общую проверку, публичное построение
и сравнение канонических байтов. Ненормализованная идентичность отклоняется,
а не исправляется. Build не вызывает Parse. Частичного результата нет.

Утверждённый корневой интерфейс чтения:
```go
type CanonicalValueKind string // null, string, list, map, set; zero invalid
func (CanonicalValue) Kind() CanonicalValueKind
func (CanonicalValue) StringValue() (string, bool)
func (CanonicalValue) Elements() ([]CanonicalValue, bool)
func (CanonicalValue) Entries() ([]CanonicalMapEntry, bool)
func (CanonicalValue) EncodedSize() int
```
Константы — CanonicalValueKindNull/String/List/Map/Set. Неверный вид или ноль
дают ноль/false; корректная пустая коллекция — пустой список не nil и true.
Списки независимы, дочерние значения неизменяемы, порядок канонический.
EncodedSize не копирует данные, для недействительного значения даёт ноль.
Используется существующий корневой разбор; конструктор байты не разбирает
и не удерживает входные данные вызывающего кода.

## 9. Размеры, ошибки и обязанности при подключении

До выделения пропорциональной памяти и сортировки проверяются исходные размеры
коллекций и строк, арифметика защищена от переполнения. Эти ограничения отличаются
от размеров итоговых деревьев: слияние литералов не обходит пределы входа.
Коллекция ограничена MaxCanonicalCollectionMembers, суммарные исходные строки —
MaxCanonicalValueBytes; сохраняются пределы отдельных строк, ключей и глубины.

Узлы строятся публичными средствами в установленных пределах. До создания
итоговой идентичности проверяются суммы NodeCount/EncodedSize всех полей.
Не нужно дублировать кодирование ради точного предварительного расчёта.
Временная память ограничена числом полей и корневыми пределами. Parse проверяет
суммы до обхода или копирования детей. Суммарные ограничения —
MaxCanonicalValueNodes и MaxCanonicalValueBytes; действует предел описания.

Используются ValidationError/ErrInvalid и существующие shape_invalid,
value_invalid, non_canonical, unknown_member, limit_exceeded. Ошибка содержит
статические пути и числовые индексы, не имена/пути/ссылки пользователя.
Смысловая ошибка отличается от последующего отсутствия возможностей,
доказательств или полномочий у поставщика.

Новые и сохранённые результаты проходят Parse через ValidateResolution, затем
проверку доказательств поставщика. Общей целостности записи недостаточно.
Допустимость проверяется до поиска готовых состояний и сохраняется по цепочке
(§7). До выполнения отдельно проверяются описания входов, образ/инструмент,
привязки, секреты/профили доступа, допустимость повторного использования,
поколение владельца, изоляция и полнота долговременных данных.
Канонический хеш не даёт прав на выполнение или доступ.

Конструктор не выполняет этих внешних действий. Существующие результаты,
записи, описания, области хеширования, другие схемы и эталонные данные
не меняются. Реализация и проверки представлены в PR #152, но ещё не включены
в неизменяемый выпуск модуля.
Выпуск — #151; ограничения проекта записаны в
[исправлениях и повторном разборе](runtime-v2-execution-schema-review.RU.md).
[Перечень тестов](runtime-v2-execution-schema-tests.RU.md) отдельно утверждён
16 октября 2026 года.

## 10. Предлагаемый выпуск модуля (#151)

16 октября 2026 года пользователь согласовал прямой выпуск проверенного коммита,
без подготовительного PR на каждую версию. Прежнее предложение PR только
с описанием выпуска отозвано. Общие [правила публикации](runtime-go-module-publication.RU.md)
и [проверки автоматизации](runtime-go-module-publication-tests.RU.md) разделяют
инструментарий H и исходники S, задают ручные режимы, внешнее описание и переход
от проверенного кандидата к окончательной версии. Подробный договор и перечень
согласованы 16 октября 2026 года; локальная реализация ещё не доказывает выпуск модуля.

PR автоматизации #153 и CI после слияния прошли. После отказа при создании
ссылки на первоначальный коммит пользователь явно согласовал
S=bf161c7cb6bf54b1ae6f8614e452963a5ddad36f для v0.6.0-rc.1 и v0.6.0.
От первоначального слияния #152 внутри модуля отличается только README;
код и тесты Go, зависимости и эталоны прежние. Тег кандидата уже закрепляет
этот S. Исправление чтения после записи должно сохранить его и продолжить
совпадающий черновик; успешный выпуск кандидата или окончательной версии
ещё не заявляется. Файл RELEASE-v0.6.0.md, новый коммит
библиотеки и подключение к приложениям не требуются. Свободный номер версии
не возобновляет #140. #151 остаётся открытой до успешных проверок публичного
прокси, контрольных сумм и внешнего потребителя. Неизменяемая версия, коммит
и ссылки на проверки записываются в её отчёте GitHub. PR с изменением дорожной
карты для каждой версии не становится условием выпуска. См.
[запись решения](../adr/2026-10-16-runtime-go-execution-schema-publication.md)
и [проверки публикации функции](runtime-v2-execution-schema-tests.RU.md#проверки-публикации-151-предложение).
