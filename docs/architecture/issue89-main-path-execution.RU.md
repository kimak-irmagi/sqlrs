# #89: подключённое штатное исполнение

Состояние реализации на 2026-11-07 в рамках утверждённого разделения поставок.
Это не расширение #170–#174 и не заявление о готовности выпуска.

## Подключённые компоненты

- Запуск использует `sqliteconn.Open`, проверенный конечный каталог схемы и
  защиту публикуемых экземпляров из очереди. Контейнерные зависимости заданы явно.
- До принятия сохраняются неизменяемые локальные корни и их защита. Привязка
  закрепляет образ платформы Docker, JDBC, настройки и идентичность управляемой БД.
- Исполнитель сохраняет намерение отдельного планирования до создания ресурсов.
  Закрытый вывод даёт метаданные; ресурсы освобождаются до добавления продолжения.
- Plan-only хранит только настоящее задание plan, предполагаемые шаги — в
  отдельном публичном представлении. Объяснение кэша сохраняет решение на момент
  проверки, возвращает HTTP 202 и отделяет решение от результата подготовки.
- Prepare пропускает кэшированный префикс и использует одну БД и одного родителя
  Liquibase для остальных вызовов CLI `update-count 1`. PostgreSQL может
  останавливаться ради снимка. Точное разрешение удаления прежнего вывода
  ограничивает хранение двумя местами. Постоянной JVM и обратных вызовов нет.
- Кэш проверяет закреплённое исполнение, печать БД и физический признак публикации.
  Экземпляр, счётчик, намерение и защита публикуются вместе. Удаление проекций
  предшествует конечному успеху и снятию защиты экземпляра.
- Известный отказ из проверенного манифеста выбирает безопасную неизменяемую
  ошибку и очищает точные ресурсы до конечного отказа. Принятая отмена вызова
  сохраняется до сигнала; перед удалением отдельно доказываются остановка и отсутствие.
- JAR передаётся и проверяется по контрольной сумме при установке в WSL, затем
  повторно проверяется вместе с установленным движком. Загрузки во время задания нет.

Настоящий запуск не использует запасной Liquibase на хосте. Независимые тесты с
явным исполнителем сохраняют прежний путь; исполнитель psql не переключается.
Прерванная или недоказанная работа остаётся с видимыми владельцами в
`recovery_required`; запуск не перепланирует её по изменяемым файлам и не повторяет
SQL. Автоматическое продолжение, защищённая передача кэша, расширенные проверки
SQLite и дополнительные правила поиска/defaults/ref остаются в #170–#173.
Начальный адаптер использует непустые локальные корни поиска.

## Проверки и оставшиеся условия

Проверки настоящего сервиса в Docker сверяют три изменения в тех же контейнерах,
данные и `DATABASECHANGELOG`, каждый снимок, точное попадание, два кэшированных
шага с одним применением, план/объяснение и отсутствие временных контейнеров до
страховочной уборки. На Windows прошли основной путь и отдельные отказ/отмена.
На Linux UID 1000 прошли отказ/отмена и функциональные утверждения основного пути;
первоначальная уборка теста упала после прямого удаления опубликованной БД.
Подготовка исправлена на штатную остановку и публичное удаление; повтор ещё идёт.

В регрессии движка две старые подготовки не передают обязательную проверку защиты;
у клиента три старые подготовки WSL не содержат JDBC. Ограниченные изменения
запрошены, но не выполнены молча. Физический путь временных каталогов macOS также
ждёт отдельного согласования подготовок. Итоговые профили, повторы Docker,
повторное сравнение с настоящим v1, CI и готовность PR ещё открыты. Прежние
96,41%/97,22% установки не описывают расширенный журнал; здесь не заявляются
95% всей поставки или завершение #89.
