# Runtime v2: взаимодействия при построении идентичности среды выполнения

Статус: порядок взаимодействий **утверждён** @evilguest 15 октября 2026 года,
задача #150. Конкретные [типы и структура компонентов](runtime-v2-execution-schema-structure.RU.md)
утверждены 16 октября 2026 года; перечень проверок отдельно согласован в тот же день. Выпуск версии
отслеживается отдельно в [#151](https://github.com/kimak-irmagi/sqlrs/issues/151).

Утверждённое уточнение по разбору от 16 октября 2026 года: конструктор получает
итоговые аргументы, среду и координаты путей, не флаги наследования исходного
описания. Исправленная структура также задаёт квалифицированные входы
и локальный профиль исполняемого файла без права повторного использования
состояний. Эти подробности утверждены; разделение определения
ресурсов, идентичности и выполнения не меняется.

## Назначение

Внешний поставщик среды должен строить её идентичность без импорта
`schemaauthor` и без использования `schemas/conformancev1` в рабочем коде.
В v0.5.0 уже есть общие объявления, каноническая идентичность расширений,
структурированные значения и результаты определения ресурсов с их хранением.
Не хватает специализированного производственного конструктора схемы.

Он добавляется в `backend/libs/runtime-go/schemas/sqlrs`. Не создаются служба
выполнения, отдельный модуль, второй тип результата определения ресурсов,
алгоритм StateID или вариант канонического кодирования. Модуль по-прежнему
использует только стандартную библиотеку. CLI, HTTP API, схема базы и рабочий
путь движка в этой задаче не меняются.

## Взаимодействия и граница доверия

```text
явно проверенное объявление, принадлежащее поставщику среды
  -> определение точных ресурсов вне семантической библиотеки
  -> точное значимое содержание + отдельные сведения о конкретном запуске
  -> специализированный производственный конструктор
  -> существующая CanonicalResolvedExtensionIdentity
  -> существующие resolver Resolution и проверяемая по схеме CacheRecord
  -> существующая привязка среды выполнения в конструкторе преобразования
  -> проверенное описание преобразования и цепочка производных состояний
```

Конструктор отвечает за классификацию и проверку поддержанных полей
идентичности. Поставщик отвечает за определение ресурсов, приём исходных данных
и достоверность переданных утверждений. Хеш фиксирует конкретные значения,
но не доказывает получение образа, замкнутость локального инструментария или
успех задания. Конструктор не выполняет ввода-вывода.

Вместо неразобранного словаря параметров используются типизированные значимые
данные. Повторно используются неизменяемые канонические значения и ссылки
на версии секретов из корневого пакета. Возвращается существующий тип
канонического расширения. Только реализация специализированных конструкторов
импортирует пакет общего определения схем. Потребителю нужны доступ к схеме
для существующего интерфейса определения ресурсов и специализированный способ
построения; копирование полей схемы или импорт проверочного примера не нужны.

## Значимое содержание

Конкретный интерфейс должен сохранять следующие категории и различия:

- Способ выполнения: локально, в OCI или внутри контейнера базы. Compose
  переводится в один из этих способов; написание YAML и имена служб не дают
  дополнительных полей идентичности.
- Точный неизменяемый образ или инструмент и явная платформа. Нельзя смешивать
  индекс образов, платформенный манифест и локальный идентификатор Docker.
  Название локального инструмента само по себе не доказывает воспроизводимость
  на другом компьютере.
- Итоговая команда и упорядоченные аргументы. Отличия наследования и пустоты
  исходного объявления разрешаются по правилам источника до построения
  идентичности. Конструктор не добавляет разбиение, оболочку и перестановки.
- Явные несекретные переменные среды и отдельно типизированные несекретные
  ссылки на версии секретов, влияющих на результат. Значения паролей и их
  обычные хеши не допускаются контрактом.
- Логический рабочий каталог и подключения, привязанные к содержимому: место
  назначения, режим доступа, правила изолированных временных записей. Путь
  внутри контейнера может влиять на результат; путь получения файлов или
  локальный путь клиента не является идентичностью.
  Типизированные координаты раскрываются после привязки. Квалифицированные
  идентичности источников и правила материализации учитывают файл/дерево
  и возможность выполнения файла.
- Логические роли служб и базы, значимый выбор цели, но не её текущий адрес,
  ссылка на контейнер или окружение, номер задания или поколение владельца.

Структуры используют существующие канонические конструкторы, ограничения
размера и запрет повторяющихся элементов. Утверждённый API
разделяет эти категории средствами типов, включая места подстановки секретов,
а не упаковывать их в произвольный JSON или один непроверяемый словарь.

## Наблюдения, хранение и совместимость

Исходные изменяемые ссылки, доказательства и версия поставщика, места получения
ресурсов, время, процессы, возможности и пригодность к переносу не входят
в значимое содержание. Их нельзя принять через диагностический тип и затем
превратить в поля идентичности. Схема не способна распознать секрет, намеренно
выданный вызывающим кодом за обычный текст. Это ограничение доверия описывается
явно, а не заменяется запретом названий полей или обещанием распознать любой
секрет.

Новая схема поставщика получает собственную явную версию. Области хеширования
canonical-v1, другие схемы и опубликованные эталонные данные сохраняют смысл.
Старые записи не мигрируют и не переосмысливаются. Публичные средства чтения
описаний и записей проверяют новую идентичность по выбранной схеме. Добавление
схемы само по себе не требует нового формата записи результатов.

`Resolve`, `Revalidate` и `Acquire` остаются за пределами конструктора.
Поставщики регистрируют эту схему в существующем механизме. Сохранённая
идентичность фиксирует содержание, но сама по себе не является полным комплектом
для повторного запуска или разрешением доступа к исходным данным, секретам
и базе.

Профиль host-executable описывает только проверенный исполняемый файл,
не все внешние зависимости. До планирования потребитель запрещает выбор
готового State, публикацию для повторного использования и общее воспроизведение;
ограничение сохраняется по всей цепочке потомков. Следующий полный инструмент
не исправляет неполного предка. Хранение записи определения ресурса — другое
действие; конструктор не реализует хранилище признаков или политику кэша.
