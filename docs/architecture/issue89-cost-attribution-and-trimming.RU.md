## 1. Сопоставление по исходникам, не по угаданным категориям Docker

Основание: выпущенная v1 `cab99c4` и измеренная v2 `668d505`; новые результаты
обязаны сохранять свои точные хеши исходников, программы и помощника. В отчёте
есть статический справочник операций и мест вызова в обеих версиях. Номера
строк — только для показа, не идентичность измерения.

| Действие | Выпущенная v1 | v2 | Соответствие |
| --- | --- | --- | --- |
| Планирование изменений | `runLiquibaseUpdateSQL` | `planNormalContainerLiquibase` | Одинаковая цель, другая реализация/время жизни |
| Применение не более одного изменения | `executeLiquibaseStep` / запуск на хосте | `executeNormalLiquibaseStep` → `invokeStep` / помощник в контейнере | Одинаковая цель, **не тождественный измеряемый код** |
| Остановка/проверка БД и ослабление прав | `PostgresConnector.PrepareSnapshot` | Тот же адаптер | Те же операции с отдельными внутренними ключами |
| Копирование/снимок состояния | `StateFS.Snapshot` в `execution.go` | Тот же интерфейс в `liquibase_normal_worker.go` | Та же операция выбранной файловой системы |
| Ужесточение прав и запуск БД | `ResumeSnapshot` внутри предыдущего шага | Тот же адаптер перед следующим шагом/публикацией | Та же операция с перенесённой границей |
| Проверка управляемой БД / закрепление состояния | `verifyManagedRuntime` / `RecordSeal` | Те же вызовы и дополнительные места проверки | Общее действие; классифицируется **место вызова**, не все проверки как новые |
| Запись заданий/состояний, публикация экземпляра | Прежний исполнитель/store/access | Штатный исполнитель/journal/access | Общая цель, другая реализация; не весь SQLite дополнительный |
| Разрешение/проверка/закрепление образа Liquibase | Нет контейнерной привязки | `bindFreshContainerLiquibase` / `InspectRunnerImage` | Дополнительная работа v2 |
| Проверка и освобождение закрытого вывода | Нет этого протокола контейнера | `ReadCompleteLiquibaseStepOutput`, `VerifyLiquibaseCapturePruned` | Дополнительная работа v2 с отдельными ключами кода |
| Журнал сессии/готовности/попыток/мест вывода | Нет соответствующего протокола | Координатор и `prepare/queue` | Дополнительный протокол, не разрешение удалить его |

Виды соответствия: `shared` — общее, `changed` — изменённая реализация,
`shifted` — перенесённая граница, `additional` — дополнительное,
`unresolved` — не установлено. Недоступное внутреннее время v1 — **не измерено**,
не ноль. Сопоставление исходников не означает равенства числа БД/контейнеров.

## 2. Ограниченный первый перечень сокращений

Убираются повторные механизмы, не требования безопасности. Это замены,
не доказательство недостижимости окружающих функций:

- **O1 — получение списка перед проверкой известного ID.** Положительные
  наблюдения runtime при вызове/чтении шага, готовности и проверке очистки уже
  имеют полный сохранённый ID и ожидаемое имя. Частный
  `inspectPresentContainer(ctx,name,id)` один раз проверяет этот ID, сверяя
  полный ID, точное имя, фазу и прежние разобранные метки. Декодер JSON общий.
  Проверки до/после и отмена сохраняются. Отказ inspect — ошибка, **не отсутствие**.
  Поиск/принятие/удаление по имени и методы отсутствия прежние. Нет кэша метаданных
  между вызовами, общего расширения интерфейсов и изменений psql.
- **O2 — повторная проверка образа внутри одной новой привязки.** После разрешения
  образ уже проверяется перед исследованием состава; в том же успешном вызове
  повтор после сохранения привязки не нужен. Вход с сохранённой привязкой проверяет
  образ один раз. Нет кэша тегов, пропуска свежего разрешения, общего кэша состава
  или неявного повторного pull после неясного эффекта. Внешняя очистка Docker может
  привести к отказу последующего create, как и после любого наблюдения наличия
  образа; подмена образа запрещена.
- **O3 — три копирования одного завершённого вывода сессии.** Один ограниченный
  `docker cp` точного каталога текущего вызова вместо трёх процессов. Отдельный
  строгий декодер архива принимает только три завершённых обычных файла и точный
  необязательный заголовок каталога. Все проверки манифеста/ID/хешей/EOF прежние,
  как и предел каждого файла, общий предел
  `2*streamLimit+8192+archiveAllowance`, общий срок, отсутствие дочерних процессов
  и наблюдения родителя до/после. Лишние, повторные, отсутствующие, связанные,
  разреженные, частичные, переименованные записи и опасный PAX запрещены.
  Нет распаковки, произвольного чтения корня/каталога, запуска или записи.
  Результат — срезы одного ограниченного буфера без дополнительных копий потоков.
  Корневой вывод планирования и отдельные файловые читатели пока прежние.
- **O4 — повторная синхронизация той же файловой системы внутри команды.** Оба
  помощника v2 передают stdout и stderr одного защищённого каталога двум командам
  `sync -f`. В каждой заменить пару на содержащий каталог: шесть завершающих
  операций синхронизации становятся четырьмя на **тех же четырёх границах фаз**.
  Последняя синхронизация после переименования манифеста остаётся. Проверки наличия/
  типа файлов, полные байты, владение, коды возврата, протокол манифеста и привязка
  хеша помощника сохраняются. Сначала проверить утилиту закреплённого образа в
  Actions; при неподдерживаемой семантике изменение не применять.

[Семантика GNU sync](https://www.gnu.org/s/coreutils/manual/html_node/sync-invocation.html)
и [реализация coreutils 9.4](https://github.com/coreutils/coreutils/blob/v9.4/src/sync.c)
подтверждают рассуждение O4, не версию утилиты в образе и не экономию миллисекунд.
Не объединять фазы синхронизации, не заменять syncfs на fsync, не убирать проверки
ID/дочерних процессов/COMMIT, не кэшировать разрешения безопасности и не удалять
иной код ради покрытия. Для новых кандидатов нужны свои свидетельства и ревью.

## 3. Измерение внутри процесса, по умолчанию выключено

Внешняя трассировка больше не предварительное условие. Обычный внутренний пакет
`internal/preparecost`, общий для prepare/runtime/DBMS через контекст, без общих
изменяемых перехватчиков. Он владеет измерениями одного prepare и фиксированными
ключами операций/мест вызова. Не даёт прав запуска/очистки и не пишет состояние БД.

Предлагается явный внутренний переключатель `SQLRS_PREPARE_COST=1` при запуске
движка, независимо от нынешнего уровня debug по умолчанию. Без нового флага CLI
или настройки API. Без переключателя: пустой получатель, нет хранения/вывода
интервалов. При включении `PrepareService` начинает запись каждого исполнителя,
передаёт её через контекст и завершает на всех выходах. Корни связывает локальный
счётчик процесса; порядковый номер обозначает логический шаг. Для разовых операций
есть фазы запуска/планирования/публикации/очистки. Не выдаются ID заданий, сессий,
контейнеров, DSN, SQL, пути, произвольные строки, аргументы и тексты ошибок.

Запись, перечень ключей, подсчёт и ограниченный транспорт — обычный код; настоящий
сценарий — интеграционный тест. Интервал содержит локальный ID/родителя, ключ,
фазу, номер шага, относительные монотонные начало/конец и фиксированный исход.
Записи изолированы/синхронизированы, чужие/неверные области отвергаются,
завершение однократное. Незакрытые/потерянные/переполненные данные делают отчёт
неполным, а не выдумывают время и не меняют результат prepare. До 32768 интервалов
на корень.

Во время исполнения данные буферизуются. После завершения — числовые/фиксированные
записи в закрытый stderr движка с точным префиксом версии, начальной/конечной
рамкой, количеством и признаком полноты. Корень времени исполнения заканчивается
последней операцией; последующая сериализация/выдача учитывается отдельно.
Конечный статус задания не ждёт диагностического вывода. После остановки
неизменного таймера API сборщик отдельно ждёт соответствующую конечную рамку
с ограниченным сроком. Нет записи журнала на горячем пути каждой операции.
Сборщик постоянно читает stderr ограниченным построчным разбором: посторонние
журналы отбрасываются без хранения/печати, принимается только фиксированная
грамматика. Выгружаются только проверенные сводки затрат. До 8 МиБ принятых данных
на процесс, строка затрат до 4 КиБ. Посторонние длинные строки читаются/отбрасываются
ограниченными частями, не накапливаются и не считаются испорченными записями затрат.
Отказ чтения/квоты делает измерение неполным и запускает
прежнюю очистку своих процессов, не молчаливый частичный успех. Поздняя/пропавшая
конечная рамка не подтверждает измерение. Сырые журналы не публикуются.

Границы измерения: разрешение/проверка образа, подготовка входов/настроек,
планирование, запуск БД/сессии, каждый вызов, чтение/проверка вывода, проверка
очистки, проверки/остановка/запуск БД, снимок/размер StateFS, вызовы журнала шага/
сессии, публикация и очистка. Вложенный транспорт Docker сохраняет ключ вызывающего
кода, но не прибавляется отдельно. Внутреннее время JVM не выводится из общего
вызова: весь интервал отмечен как изменённая реализация, неизмеренные внутренние
расходы JVM остаются явными.

### Внутренние фазы помощника без новых JVM и отдельной программы

При явном включении измерений доверенный помощник v2 также измеряет свои фазы:
проверки/очистку до запуска, CLI, дочитывание потоков, синхронизацию потоков,
хеширование/переименование, синхронизацию переименованных потоков, подготовку/
синхронизацию манифеста, окончательное переименование/синхронизацию. Встроенная
команда оболочки `read` читает `/proc/uptime`: время от загрузки с **разрешением
10 мс**, не отдельный процесс `date` и не календарные часы. Выключенный режим
не читает часы и не выдаёт записи. [Код Linux 6.8](https://github.com/torvalds/linux/blob/v6.8/fs/proc/uptime.c)
показывает источник и вывод сотых долей секунды. Наличие проверяется в закреплённом
образе. Эти измерения нельзя выдавать за наносекундную точность.
Движок явно задаёт переключатель помощника из состояния записи; окружение образа/
запроса не может включить его или перенаправить измерения в вывод CLI.

Только фиксированные фазы/числа выдаются в собственный stdout помощника через
Docker, не в закрытые stdout/stderr Liquibase; до 4 КиБ на вызов. Runtime закрыто
разбирает их и связывает с текущим вызовом. Нет отдельного файла, поля манифеста/
схемы или полномочий запуска. Ошибка часов/формы не меняет исполнение/код выхода
и не выдумывает нулевые затраты: подробности помечаются неполными. Семантика
выключенного помощника прежняя, но новые байты требуют нового закреплённого хеша.

Смещения/длительности помощника и разрешение сохраняются отдельно от монотонных
интервалов хоста: положение внутри вызова Docker не выдумывается. Короткая фаза
может округлиться до нуля; это отличается от отсутствия измерения. Неопределённость
до 10 мс на фазу показывается явно, накопленная — отдельно. Время от загрузки
включает приостановку; его семантика не выдаётся за семантику часов Go.
Несогласованные/переполненные/обратные отсчёты или длительности, несовместимые
с содержащим вызовом хоста, делают подробности недостоверными, не ломают prepare.
Обнаружение любой возможной смены пространства времени не обещается.
Это вложенная несуммируемая
детализация общего вызова, не добавка к суммируемым затратам хоста. Так получаем
затраты конкретного кода помощника, включая sync, без знания внутренностей Java
и без удаления границ сохранности.

### Завершение передачи подробностей (утверждено 2026-11-11)

Утверждённый объём не меняется. До подключения фаз помощника и стоимости выдачи
отчёта явно фиксируются оставшиеся решения внутреннего формата и владения:

- `Report` владеет временными наблюдениями помощника, привязанными к существующему
  локальному интервалу вызова планирования либо шага. Доверенный хост выбирает
  владельца и измеряет содержащий вызов. Дочерний вывод передаёт только восемь
  фиксированных внутренних фаз. Чужой/повторный владелец, неверные часы или
  неполные фазы не подтверждают подробности; сырые строки/ошибки не сохраняются.
- Прежние begin/span/end остаются. До end добавляются закрытые записи `helper`:
  корень, владелец, фиксированная фаза, начало/конец в сотых секунды и длительность
  содержащего вызова. Вместо них допустима явная отметка `unavailable` владельца.
  Разрешение — 10 мс; положения на шкале хоста и добавки к его сумме нет.
- После успешной полной записи выдаётся одна закрытая запись `observer` того же
  корня: длительности кодирования, ожидания блокировки писателя и записи отчёта.
  Блокировка охватывает обе записи. Это **не полная стоимость наблюдения**:
  копирование снимка и создание/запись самой отметки observer явно остаются
  неизмеренными. Парные серии с записью/без неё оценивают всё влияние; поправки
  отдельных строк и кругового «измерения самого себя» нет.
- Полный измеряемый вариант ждёт end **и** observer только после остановки
  прежнего таймера API и в прежний ограниченный срок. Частичная запись, пропавшие/
  поздние сведения либо неполные ожидаемые фазы запрещают признать отчёт полным,
  но не меняют результат prepare. Прежняя точная очистка сохраняется.
- Движок явно переопределяет флаг помощника при каждом запуске/вызове; serve,
  готовность и читающая проверка очистки остаются выключенными. Без записи нет
  дополнительных чтений часов/вывода. Таймеры не меняют код CLI, байты захвата,
  границы sync или права очистки. Нет новых API, версии манифеста, схемы БД либо
  сохранённых в БД измерений.

Критический и повторный разбор исправили круговой подсчёт накладных расходов,
раннее признание отчёта по одному end, дочернее назначение владельца, сложение
разных шкал, потерю исхода CLI при отказе часов, отсутствие явного выключения и
общие изменяемые снимки. Оставшихся P0–P2 в этом уточнении не обнаружено.
Требования входят в CT06–CT11/CT14; точные проверки формата и адресные изменения
прежних подготовок предложены как DT01–DT08 / OT-CT05–OT-CT08 в
[перечне тестов](issue89-cost-attribution-and-trimming-tests.RU.md). @evilguest
утвердил уточнение компонентов ответом «Утвердить уточнение передачи»; точное время
ответа недоступно. Затем отдельно утверждены DT01–DT08 и разрешены OT-CT05–OT-CT08;
идёт реализация, начиная с тестов.

## 4. Подсчёт и нужный отчёт

Знаменатель `PrepareElapsedMS` — прежний полный таймер API сборщика, включая
принятие/ожидание/ответ вне корня исполнителя. Непокрытые части остаются
нераспределёнными, не объявляются SQLite. Время корня и накладные расходы
наблюдения показаны отдельно. Для длительностей операций не нужно вычитать
часы разных процессов; прежние данные сохраняют прежние правила часов.

Для каждой операции/места вызова и шага:

- соответствие v1 и точный символ исходников/версия;
- фактическое число вызовов, сумма и распределение длительностей, включая отказы;
- время с потомками и собственное время без объединения интервалов потомков;
- `ZTotalMS` — объединение интервалов операции за prepare;
- `Zratio = 100 * ZTotalMS / PrepareElapsedMS`;
- общее число и среднее на вызов, а также значения по шагам. Среднее на вызов
  не равно среднему на шаг: видны шаги без вызовов/с кэшем и разовые фазы.

Объединения категорий могут пересекаться и помечены **несуммируемыми**. Сводка,
которую можно складывать, использует собственное время и нераспределённое время;
пересечение параллельных ветвей выделяется отдельно, а не приписывается дважды.
Проверяются вложенность, счётчики, конечные неотрицательные длительности,
полнота рамок и связь с корнем/шагом. Проценты разных уровней не складываются.

Пример формы, **не измеренные числа**: `шаг 3 | capture.read |
ReadCompleteLiquibaseStepOutput | дополнительное | N вызовов | Z мс | за prepare
ZTotal мс | Zratio %`. Отдельная таблица показывает общие/изменённые/перенесённые
