# План тестов обнаружения провайдеров входа в CLI

Статус: утверждено владельцем продукта 2026-10-23 после критического разбора.
Проверяются согласованные
[синтаксис](../user-guides/sqlrs-auth-providers-proposal.md),
[поток](cli-auth-provider-discovery-flow.RU.md) и
[структура компонентов](cli-auth-provider-discovery-structure.RU.md).

## Уточнения контракта, предлагаемые вместе с тестами

- Для повторного запроса авторитетен effective endpoint существующего command
  context: профиль задаётся `--profile`, а глобальный `--endpoint` временно
  переопределяет адрес только на этот вызов. `auth providers` ничего не сохраняет.
- И human, и JSON-списки сортируются по ID. JSON содержит ровно один массив
  `providers` верхнего уровня, элементы — только `id`, `display_name`, `adapter`.
- Ответ публичного provider-list, включая тело HTTP-ошибки, ограничивается
  1 MiB до JSON-декодирования или разбора ошибки.
  Это предложенная защита клиента, не ограничение OpenAPI или сервера.
- Human-вывод обезвреживает CR, LF, управляющие/терминальные escape-символы,
  форматирующие Unicode-символы и разделители строк/абзацев в именах от
  сервера; JSON сохраняет исходное значение со стандартным экранированием JSON.
- Ошибки разделяются по причинам: `no enabled login providers`,
  `invalid provider catalogue`, `cannot fetch provider catalogue`. Тесты
  проверяют категории, а не случайную формулировку всего предложения.

## Тесты до реализации

| ID | Уровень | Сценарий и ожидаемый результат |
| --- | --- | --- |
| P01 | `internal/client` | Получить корневой список с одним и двумя провайдерами. Проверить точный GET path, три публичных поля и отсутствие `Authorization`/`Cookie` при настроенном client auth token. |
| P02 | `internal/client` | Запросить endpoint с префиксом организации без удаления префикса. Same-origin redirect успешен; cross-origin и HTTPS-to-HTTP redirects отклоняются без пересылки credentials. |
| P03 | `internal/client` | Отвергнуть отсутствующий/null `providers`, лишние поля, некорректный/дополнительный JSON, неправильные/повторные ID, пустые имена/adapter, неправильный content type и успешное либо ошибочное HTTP-тело > 1 MiB; проверить точную границу размера. Пустой `providers: []` остаётся допустимым wire response. |
| P04 | `internal/client` | HTTP 503, timeout и некорректный ответ отличимы от корректного пустого списка; нет подстановки из кэша или жёсткого значения. |
| P05 | интеграция CLI-процесса | Инициализировать remote workspace, потерять вывод init, запустить **новый процесс CLI** из сохранённого workspace и выполнить `auth providers` без повторного init. Изменить каталог сервера и повторить в ещё одном процессе: вывод меняется, байты config — нет. Это основной сценарий. |
| P06 | `internal/app` | Default profile, явный `--profile`, endpoint с префиксом организации и глобальный `--endpoint` обращаются только к effective server. Override действует один вызов. |
| P07 | renderer | Human output сортирует ID, показывает имя каждого провайдера и синтаксически безопасный пример входа. CR/LF/escape в display name не создают лишних строк или команд. JSON валиден, отсортирован, содержит ровно три публичных поля и не содержит human-подсказки, токенов, деталей провайдера или членства. |
| P08 | `internal/app` | Local mode и отсутствующий/некорректный effective remote endpoint отклоняются до HTTP, запуска daemon/engine, браузера и credential store. |
| P09 | `internal/app` | Пустой список, некорректный каталог и недоступный сервер дают три разные категории ошибки без прежнего списка/Google и без частичного успешного вывода. |
| P10 | `internal/app` init | Новый token-free init с одним/двумя провайдерами и `init remote --update` при смене endpoint показывают только результат своего discovery **после** успешной записи config. Каталог/выбор не сохраняются; прочие настройки переживают update. |
| P11 | `internal/app` init | Сбой discovery, записи config, dry-run и устаревший bearer-token init не печатают ложный готовый к входу список. |
| P12 | parser/help | `auth providers` не принимает лишних positional args и неподдерживаемых флагов; `sqlrs auth --help` и `sqlrs auth providers --help` показывают команду. `auth login` без провайдера остаётся ошибкой и указывает `sqlrs auth providers`. |
| P13 | регрессия | Явный `auth login <provider-id>` по-прежнему напрямую запрашивает детали без предварительного списка. Существующие тесты `auth status`/`auth logout` запускаются, а не дублируются. |

После утверждения необходимо сопоставить имеющиеся auth/init/client tests с
этими требованиями и сообщить о противоречиях до изменения тестов. Сначала
пишутся новые тесты, затем production code. Запускаются целевые и все
релевантные CLI tests, измеряется покрытие изменённого кода (цель 100%,
минимум 95%); для повторного повышения покрытия используется требуемое
согласование.
