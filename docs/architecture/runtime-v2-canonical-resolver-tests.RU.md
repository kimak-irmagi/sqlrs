# Каноническое разрешение Runtime v2: перечень проверок

Состояние: перечень проверок утверждён @evilguest для #146/#147, 2026-10-01.
Основания: [порядок взаимодействия](runtime-v2-canonical-resolver-flow.RU.md)
и [устройство компонентов](runtime-v2-canonical-resolver-structure.RU.md).

Проверки описывают открытый договор, а не устройство вспомогательных функций.
В версии 0.5.0 результат разрешения канонический. Записи прежних выпусков
остаются свидетельством работы именно тех выпусков; текущий декодер не
принимает их строковый формат. Часть проверок возможна в запросе на
изменение, а проверка публикации — только после его включения в основную ветку.

| Код | Этап | Что проверяем |
| --- | --- | --- |
| CR01 | Запрос | Потребитель из другого пакета через открытый интерфейс схемы создаёт испытательного поставщика, регистрирует его в существующем реестре и получает `CanonicalResolvedExtensionIdentity` через `ResolveCurrent`, не обращаясь к закрытым пакетам или второму механизму разрешения. Создание схемы поставщиком и обычное использование результата проверяются как разные уровни доверия. |
| CR02 | Запрос | Четыре испытательных поставщика для файла, OCI, Git и пакета используют разные схемы описания, правила приведения, схемы идентичности и типизированные поля. Каждый проходит через один координатор и хранилище. Выбор учитывает роль, владельца, вид и схему; повторы, отсутствие поставщика, неверное описание, несовпадение схемы и неизвестное расширение дают устойчивые коды ошибок. Настоящие сетевые клиенты не нужны. |
| CR03 | Запрос | Поставщик со счётчиками доказывает, что приведение описания предшествует построению ключа. Равнозначные варианты получают один ключ, разные физические рабочие области и версии правил — разные. Обнаружимое несовпадение схемы — тип поля, правило раскрытия или обязательность — отвергается при чтении или проверке и не даёт `CURRENT`. Изменение только смысла поля кодек обнаружить не может: поставщик обязан повысить версию правил. |
| CR04 | Запрос | Методы чтения канонической идентичности возвращают владельца, вид, схему и упорядоченные типизированные поля, не позволяя изменить исходную идентичность. Кодек отвергает несовпадение идентичности и схемы. |
| CR05 | Запрос | Заранее проверенные эталоны, полученные по точному описанию формата независимо от проверяемого кодека, фиксируют JSON, канонические байты, отпечатки полей и всей идентичности для текста, вложенного составного значения и ссылки на секрет, включая поля с ограниченным раскрытием. Запись и чтение сохраняют их типы, полные значения и правила раскрытия; ссылка не содержит значение секрета. |
| CR06 | Запрос | Чтение по схеме отвергает отсутствующие, лишние и повторные поля, неверный тип или правило раскрытия, отсутствие обязательного поля, повреждённое составное значение, неверную ссылку, поддельные отпечатки, неправильный порядок, неизвестные и повторные поля JSON, неверный UTF-8 и непарные суррогаты, лишние данные, `null` и превышение ограничений. Повреждения вносятся на каждом уровне вложенности; частичный результат и неограниченное выделение памяти недопустимы. |
| CR07 | Запрос | `CacheRecord` сверяется с независимо вычисленными байтами записи, отпечатком рабочей области, ключом и контрольной суммой. Он сохраняет весь результат, копирует входные данные и проверяет все части ключа. Изменённые смысловые поля с заново вычисленной правильной внешней суммой всё равно отвергаются; отдельно проверяются неверные сумма и версия, превышение 4 МиБ, 4096 полей или 64 уровней JSON, а также повторные, неизвестные и лишние поля. Новый декодер отвергает старую строковую запись, а отдельный потребитель со старой версией — новую. Преобразования нет. |
| CR08 | Запрос | При `CURRENT` нет повторного вычисления и получения объекта; каноническое представление остаётся прежним, обновлённые служебные сведения проверяются и сохраняются до ответа. Неверные новые сведения и ошибка записи возвращают ошибку, а не обещание сохранённого результата. |
| CR09 | Запрос | `STALE` и `UNKNOWN` запускают повторное вычисление без получения объекта и сохраняются в результатах или ошибках. Таблица отказов охватывает отсутствие записи, повреждение и несовместимую версию, неверный сохранённый или новый результат, неверный ответ повторной проверки, ошибки вычисления и записи, отказ в доступе, ввод-вывод и отмену. Для каждого случая сверяются операция, код, прежнее состояние и причина, число вызовов и отсутствие частичного результата. |
| CR10 | Запрос | Один процесс записывает типизированную запись, другой читает её. Завершение до атомарной замены оставляет старую запись либо отсутствие записи; после замены обычный запуск другого процесса видит целую новую запись. Отдельно подставленная ошибка синхронизации каталога возвращается как ошибка сохранности без обещания пережить отключение питания; успешные вызовы синхронизации файла и каталога наблюдаются. Завершение процесса не выдаётся за испытание отключения питания. Параллельные процессы и читатели не видят частичных записей; доверенный каталог и запрет ссылок сохраняются. |
| CR11 | Запрос | Ограниченная очистка удаляет только подходящие канонические записи, пропускает временные файлы, повреждённые внешнюю оболочку, сумму или ключ записи и старые версии, не проходит по ссылкам. Она не обещает проверить поля идентичности без схемы поставщика. |
| CR12 | Запрос | Переведённый файловый поставщик выдаёт каноническое `content.digest`, сохраняет защиту путей и явное получение только проверенного неизменяемого объекта. Проверки на Linux, macOS и Windows охватывают `CURRENT` для неизменного файла, запрет ложного `CURRENT` после замены байтов той же длины с восстановленным временем, `STALE` после удаления, замены не-файлом и смены размера, `UNKNOWN` при слабых или неполных свидетельствах. Для каждого включённого класса файловой системы остаётся обязательная проверка на соответствующей платформе. |
| CR13 | Запрос | Адаптер SQLite использует прежнюю таблицу и схему БД, но новый формат записи; читает после повторного открытия, сверяет ключ в индексе и внутри записи, атомарно меняет служебные сведения. Несовместимая версия строки таблицы и старая версия самой записи проверяются отдельно. Остальные таблицы и обычный путь исполнения не меняются. |
| CR14 | Запрос/выпуск | Один набор исходников внешнего потребителя запускается из подготовленного локального и опубликованного общедоступного хранилищ модулей с `GOWORK=off`, без `replace`, автоматически созданной версии по номеру изменения или соседней рабочей копии. Через открытые пакеты он доказывает регистрацию, вычисление, `CURRENT`, сохранение всех трёх типов полей после запуска другого процесса и отказ от старой записи. |
| CR15 | Запрос | Опубликованные канонические отпечатки, идентификаторы состояний и эталонные данные старого семантического ядра остаются побайтово прежними. Старая запись механизма служит образцом для проверки отказа, а не успешного чтения. Действующие проверки механизма, SQLite и внешнего потребителя обновляются под канонический договор; ни одна не пропускается. |
| CR16 | Запрос/выпуск | Задания непрерывной проверки и выпуска явно запускают новую случайную проверку декодера идентичности и записей, существующую проверку путей, модульные и платформенные проверки, поиск гонок, канонический набор, состав зависимостей и построчное покрытие на выпускаемом изменении. Цель покрытия — 100%, допустимый минимум — 95%; при недоборе до цели нужен отдельный построчный план повышения и его утверждение. |
| CR17 | Выпуск | Проверки выпуска требуют, чтобы описание версии 0.5.0 называло изменение интерфейса Go, новый формат, отсутствие преобразования старых данных, лицензию, зависимости, суммы и подтверждаемое происхождение. Предварительная и окончательная версии указывают на одно проверенное изменение после слияния; исходники, суммы и подтверждения совпадают с общедоступным хранилищем модулей. Сам запрос на изменение не может закрыть #147 до завершения публикации. |

## Правила эталонов и запуска

- Эталоны CR05/CR07 строятся по
  [точному описанию формата](runtime-v2-canonical-resolver-structure.RU.md#точный-формат-записи-версии-050):
  оно задаёт поля JSON, кодирование и порядок значений, исходные данные
  для ключа и суммы, ограничения размера. Тест проверяет формат, а не задаёт его.
- Ожидаемые канонические байты, JSON, отпечатки полей и записей заранее
  проверяются по описанию формата и сохраняются в репозитории. Проверяемый
  код не вычисляет для себя ожидаемый результат.
- При проверке смысловых повреждений меняется одно поле, а правильная
  внешняя контрольная сумма вычисляется заново независимым испытательным
  кодом. Зависимый отпечаток поля, всей идентичности или ключ намеренно
  остаётся несогласованным: иначе проверка доказала бы лишь отказ по неверной
  сумме. Неверная сумма проверяется отдельно. Полностью согласованную
  подмену владельцем доверенного каталога отклонить нельзя: контрольная
  сумма не служит подтверждением подлинности.
- Два направления отказа между версиями проверяются в отдельных сборках
  модуля: Go не подключает две версии одного модуля в одну программу.
  Для запроса на изменение старую версию можно подготовить локально из
  неизменяемой метки; при выпуске используются общедоступные модули.
- Проверки сравнивают коды и результаты, не выводя значения полей с
  ограниченным раскрытием в сообщения об ошибках. Полные значения таких
  полей могут храниться в доверенном каталоге; это не шифрование на диске.
- Проверки файлов на трёх платформах требуют подтверждения для включённых
  классов файловых систем. Для неизвестных и слабых свидетельств ожидается
  `UNKNOWN`, а не ложный `CURRENT`.

Для CR09 эталоном служит существующий договор наблюдаемых ошибок: отсутствие,
повреждение и несовместимость записи приводят к новому вычислению с причинами
`cache_miss`, `corrupt_cache` и `incompatible_cache`; непроверенный результат
поставщика даёт `invalid_cached_resolution`. Если вычисление после `STALE` или
`UNKNOWN` не удалось, ошибка указывает операцию `resolve`, точное прежнее
состояние и причину. Неверный новый результат или обновлённые сведения дают
`validate_resolution` и `invalid_resolution`. Ошибка ввода-вывода или отмена
при чтении и записи указывает `cache_load` или `cache_store` с соответствующим
устойчивым кодом и не запускает повторное вычисление.

## Сверка существующих тестов после утверждения перечня

Сверка выявила три группы противоречий. Тесты разрешителя создают прежний
`Resolution.Identity` и вызывают кеш по старым сигнатурам. Тесты текущей
записи кеша и внешнего потребителя ожидают успешного чтения и повторной записи
образца версии 0.2.0. Тесты файлового поставщика и SQLite проверяют прежние
строковые поля. Их нужно перевести на утверждённый канонический договор;
образец версии 0.2.0 станет проверкой отказа, а не успешного чтения. Исторические
эталонные тесты смыслового ядра и свидетельства опубликованных версий не
противоречат новому договору и остаются без изменений. Пользователь подтвердил
обновление старых тестов; ни одна проверка не будет пропущена. Других
противоречий при этой сверке не обнаружено.

## Утверждённый план повышения покрытия и результат

Полный отчёт для Windows от 2026-10-02 показывает 4274 проверенных оператора
из 4523 (94,5%). Для допустимого минимума 95% нужно проверить ещё хотя бы 23.
Построчный отчёт сохранён в рабочем сеансе. Больше всего непроверенных
операторов в `canonical_extension_json.go` (30),
`resolver/directory_cache.go` (22), `canonical_builder_v1.go` (17) и
`json_helpers.go` (17). Этот план не ослабляет тесты или порог покрытия.

1. Сопоставить 30 операторов в кодеке с требованиями CR04–CR07. Добавить
   проверки через открытый интерфейс для предельного числа полей и неверных
   значений, имён, вариантов полезной нагрузки, Юникода и вложенности — там,
   где это действительно предусмотрено договором. Ветви, до которых нельзя
   дойти после проверки построителем идентичности, удалить как мёртвый код,
   не придумывая тесты для невозможных внутренних состояний.
2. Сопоставить 22 оператора файлового кеша с CR07, CR10 и CR11. Проверить
   предусмотренные ошибки чтения, записи и синхронизации, повреждённые записи
   и очистку через контролируемую файловую систему или узкую подстановку
   ошибки. Сохранить работу на всех платформах; завершение процесса не считать
   имитацией отключения питания.
3. Повторить все тесты модуля и построчное измерение. Если результат останется
   ниже 95%, затем разобрать `canonical_builder_v1.go` и `json_helpers.go`:
   проверять только описанное внешнее поведение либо удалять мёртвый код.
   Перед ещё одним циклом повышения покрытия снова запросить разрешение.

Исторические эталонные проверки и утверждённый перечень канонических тестов
сохраняются; проверки не пропускаются.

Пользователь утвердил этот план. Проверки на внешней границе теперь охватывают
неверный JSON типизированной идентичности, Юникод и вложенность, повреждённый
JSON кеша, а также ограничение в 4096 полей при кодировании и чтении. Полный
прогон модуля runtime-go от 2026-10-02 прошёл: проверено 4297 из 4523
операторов (95,003% без округления), что выше допустимого минимума 95%.
Проверки невозможных внутренних состояний и дополнительные вмешательства в
рабочий код только ради покрытия не понадобились.
