# Runtime v2 persistence: test design

Status: approved by the user for issue #110 after a second critical design
review, 2026-09-27.

Version note: the resolver-cache assertions below are historical #110 release
evidence. The v0.5.0 canonical record and SQLite adapter require the new
[canonical resolver test plan](runtime-v2-canonical-resolver-tests.md).

This plan verifies the approved
[interaction flow](runtime-v2-persistence-flow.md) and
[component/schema design](runtime-v2-persistence-structure.md). Tests exercise
public semantic contracts and persistent invariants rather than private helper
layout. No test switches the default prepare/runtime path to Runtime v2.

## 1. Test layers and fixtures

- Public `runtime-go/resolver` tests cover the opaque `CacheRecord` codec and
  preserve the published v0.2.0 cache wire format.
- Local-engine unit tests cover closed `runtimev2store` DTOs and validation.
- SQLite integration tests use both isolated in-memory databases and file-backed
  databases reopened by a new store instance. Restart, upgrade, transaction, and
  durability assertions are file-backed.
- A checked-in representative rc.6 database fixture is generated by a pinned
  historical rc.6 revision, not handcrafted by current code. It contains legacy
  states, instances, names, queue data, settings/unrelated objects, and no v2
  marker; its generator revision and checksum are recorded.
- Independent golden persistence rows are authored from reviewed public Runtime
  v2 JSON and identity vectors without calling the SQLite adapter under test.
- Corruption tests mutate a disposable fixture only through an explicitly
  test-only raw connection with foreign keys/check constraints disabled before
  the normal store is reopened. Production APIs never expose this bypass.
- Failure injection covers transaction begin/statement/commit, cancellation, and
  schema-installation boundaries. A pre-commit failure must roll back; an
  ambiguous commit may expose only a complete old or complete new generation,
  and an idempotent retry must converge to the new one. Tests never rely only on
  mocks for acceptance criteria that concern SQLite constraints or restart.
- Timestamps and generated materialization IDs use injected deterministic
  sources; tests do not depend on wall-clock ordering.

## 2. Public cache-record contract

- **CR-01 — v0.2.0 wire compatibility:** decode checked-in cache records written
  by runtime-go v0.2.0, match their full keys, and re-encode byte-identically with
  the same checksum and `sqlrs.resolution-cache.v1` schema.
- **CR-02 — construction and round trip:** construct a `CacheRecord` from every
  supported declaration role, marshal/decode it, and preserve key, descriptor,
  normalized declaration, resolution identity, and provider evidence.
- **CR-03 — full-key matching:** independently change key digest, workspace
  scope, role, owner, kind, specification schema, resolver semantic version, and
  normalized declaration; `Matches` must reject each change.
- **CR-04a..j — strict trust-boundary matrix:** `a` unknown member, `b`
  duplicate member, `c` null required member, `d` missing required member, `e`
  trailing token, `f` oversized input, `g` invalid checksum, `h` unsupported
  schema, `i` malformed identity, and `j` invalid zero value each assert the
  documented resolver error.
- **CR-05 — defensive copies:** mutations of constructor inputs and values
  returned by `Resolution()` cannot alter a record or its later serialization.
- **CR-06 — adapter conformance:** `DirectoryCache` and an in-memory reference
  adapter using `CacheRecord` return the same hit/miss/corrupt/incompatible
  outcomes and preserve existing atomic-publication tests.
- **CR-07 — public module consumption:** a standalone `GOWORK=off` consumer
  compiles against the additive API in the normal PR suite.
- **RG-01 — release-only verification:** v0.3.0 RC/GA verification separately
  repeats the clean-consumer, public-proxy, checksum, race, fuzz-smoke,
  dependency, and coverage gates without moving v0.2.0 tags; it is not presented
  as a normal unit/integration test.

## 3. Schema installation and upgrade safety

- **SC-01 — fresh install:** create the exact marker, tables, indexes, foreign
  keys, CHECK constraints, and UPDATE/DELETE triggers in one transaction.
- **SC-02 — canonical DDL and constructor parity:** the schema-sync check proves
  that `schema.sql` is the sole Runtime v2 DDL source and the architecture block
  is generated from it; `sqlite.Open`, `sqlite.New`, and the explicit ensure
  wrapper invoke the same installer and produce the same normalized object
  manifest rather than comparing incidental `sqlite_master` whitespace.
- **SC-03 — managed startup parity:** fresh and already-managed
  `managedstore.Initialize` paths install/verify the same v2 schema; the later
  `sqlite.New` call is an idempotent verification.
- **SC-04 — restart idempotence:** close/reopen repeatedly without changing the
  marker, normalized object manifest, records, or timestamps.
- **SC-05 — populated rc.6 upgrade:** start from the checked-in fixture, add the
  v2 schema, and prove every legacy and unrelated row/object remains unchanged.
- **SC-06 — real rc.6 rollback/disable compatibility:** after v2 installation,
  run the pinned historical rc.6 compatibility harness against a copy, perform
  representative legacy CRUD, reopen with current code, and prove that the old
  binary ignored reserved tables without reinterpreting or damaging either
  namespace.
- **SC-07a..i — collision/shape refusal matrix:** `a` wrong object kind, `b`
  case-insensitive reserved-name collision, `c` missing object, `d` extra or
  reordered column, `e` altered index columns/order, `f` altered foreign-key
  action/check, `g` altered trigger body, `h` malformed marker row, and `i`
  unknown version each fail before mutation.
- **SC-08 — atomic and ambiguous failure:** inject cancellation and every
  reachable DDL/commit failure. Pre-commit failures leave the old schema;
  ambiguous commit failures may reveal only the complete old or complete v2
  schema after reopen, and retry must converge to verified v2.
- **SC-09 — constraint/connection enforcement:** prove every constructor has
  `foreign_keys=ON` and `busy_timeout=0`, then prove foreign keys, size/version
  checks, immutable UPDATE triggers, and out-of-scope DELETE triggers fail
  closed.

## 4. Logical states, identities, and provenance

- **ST-01 — recipe restart round trip:** persist factory-only, one-step, and
  multi-step `RecipeLineage`; reopen and recover identical StateIDs,
  fingerprints, resolved identities, parent links, and endpoint.
- **ST-02 — relative lineage:** persist a suffix from a known anchor and recover
  the complete root-to-endpoint traversal; reject a missing anchor atomically.
- **ST-03 — logical-only state:** persist and retrieve states with zero
  materialization rows.
- **ST-04 — idempotent identity:** repeating the same lineage and canonical
  identity succeeds without rewriting `stored_at` or duplicating observations;
  the first `observed_at` survives observation deduplication.
- **ST-05 — multiple diagnostics:** two provenance values with the same resolved
  identity but different declaration spelling or resolver observation produce
  one State and two recoverable observations through the page API, not a
  conflict.
- **ST-06 — observation deduplication:** equal canonical provenance is stored
  once; an injected digest collision with different canonical bytes fails and
  leaves the original observation intact.
- **ST-07 — identity conflict:** an injected row presenting a different resolved
  identity under an existing StateID is corruption and is never overwritten.
- **ST-08a..g — strict reconstruction matrix:** use the test-only corruption
  harness to tamper independently with record version, state kind/JSON/ID,
  parent copy, resolved identity, observation type/identity, and timestamps;
  every stable case ID returns no partial record.
- **ST-09a..d — lineage corruption matrix:** fixtures bypass constraints only to
  create missing parents, cycles, discontinuous edges, and traversal beyond
  `runtimev2.MaxTransforms + 1`; each case fails closed.
- **ST-10 — transaction rollback/ambiguity:** failure after any
  parent/state/observation insert rolls back before commit. An ambiguous commit
  exposes one complete generation after reopen and identical retry converges.
- **ST-11 — concurrent writers:** same-lineage writers converge idempotently;
  different valid observations both survive; conflicting injected identities
  produce one winner plus a bounded corruption error.
- **ST-12 — independent persistence oracle:** open independently authored golden
  rows and recover the reviewed public States, StateIDs, fingerprints,
  identities, provenance, and indexed copies; a dependency/static check prevents
  the adapter from duplicating StateID or fingerprint derivation.
- **ST-13 — timestamps and observation order:** offsets and fractional
  precisions normalize to fixed-width UTC nanoseconds; invalid/out-of-range
  values fail; observations return in first-persisted `insertion_seq ASC` order
  without exposing the sequence. Pages enforce row/32-MiB budgets, reject invalid
  or wrong-state cursors, exclude post-high-water inserts from an active
  traversal, and expose them to a new traversal. Exact below/equal/above byte
  budget cases use the documented payload-size formula.

## 5. SQLite resolution-cache adapter

- **RC-01 — miss/store/load/restart:** a miss becomes a hit after `Store` and
  remains an identical validated hit after closing and reopening the engine DB.
- **RC-02 — strict v2 isolation:** representative legacy cache/state rows,
  including lookalike identifiers, can never satisfy `Load`.
- **RC-03 — indexed/envelope agreement:** mismatch between the indexed cache key
  and embedded record, or between any incoming and embedded key constituent,
  returns `ErrCorruptCache` rather than a hit.
- **RC-04 — replacement semantics:** exact-key replacement atomically updates
  resolution/evidence while previously stored logical State records remain
  unchanged.
- **RC-05 — invalidation classification:** missing, corrupt, incompatible,
  permission/storage, and cancellation outcomes match the public resolver cache
  contract; only allowed invalidations may fall back in `Manager`.
- **RC-06 — provider validation boundary:** generic load validates the envelope
  and identity, while `Manager` still invokes the selected provider's
  `ValidateResolution` before evidence is used.
- **RC-07 — failure atomicity and concurrency:** pre-commit failures retain the
  old record; ambiguous commit failures and same-key concurrent writers expose a
  complete old or new record, never mixed key, identity, or evidence. Reopen and
  identical retry converge to the requested new record.

## 6. Materialization associations

- **MT-01 — cardinality and pages:** one State has zero, one, and more than 100
  distinct materializations without changing its identity. Pages never exceed
  the requested 1..100 limit, have no duplicates/gaps, return a terminal empty
  cursor, and reject zero/over-limit values and malformed, wrong-state, or
  unsupported-version cursors. A first-page insertion-sequence high-water mark
  excludes concurrent later inserts, including backdated rows, from the current
  traversal; a new traversal sees them. The 32-MiB byte budget may shorten a
  page, always returns at least one valid item, and resumes without gaps.
  Exact below/equal/above cases use the documented payload-size formula.
- **MT-02 — named components:** persist zero, one, and multiple named components
  and recover all metadata after restart.
- **MT-03 — order independence:** permutations of the same component set are one
  canonical materialization and return name-sorted components.
- **MT-04 — idempotence/conflict:** an identical duplicate succeeds without
  rewriting timestamps; any metadata/component difference under the same
  materialization ID fails without replacement.
- **MT-05 — state boundary:** reject malformed or unknown Runtime v2 StateIDs and
  never associate a materialization with a legacy-only state.
- **MT-06a..k — bounds/JSON matrix:** `a` materialization ID, `b` identifier
  field, `c` runtime/job ID, `d` locator, `e` component count, `f` signed size,
  `g` UTF-8/control characters, `h` metadata byte size, `i` duplicate key, `j`
  non-object JSON, and `k` trailing token each cover min/max/over-limit variants.
  `c` distinguishes empty from absent; `f` includes 64-bit boundaries.
- **MT-07 — immutable lifecycle:** UPDATE and DELETE attempts fail through both
  store API absence and SQLite triggers; later GC behavior is not invented by
  these tests.
- **MT-08a..d — corrupt-read matrix:** the test-only bypass creates malformed
  metadata, an orphan component, a version mismatch, and an invalid component;
  each stable case ID returns no partial materialization.
- **MT-09 — transaction rollback/ambiguity/concurrency:** a component or
  pre-commit failure leaves no header/orphan subset; ambiguous commit permits one
  complete generation and converges on retry. Identical concurrent inserts
  converge and conflicting ones preserve one complete immutable record.
- **MT-10 — deterministic order/time:** components are name-sorted; pages use
  newest-persisted `insertion_seq DESC` without exposing the sequence; equivalent
  RFC 3339 instants canonicalize to fixed-width UTC nanoseconds and the first
  duplicate timestamp survives.

## 7. Classification and legacy separation

- **CL-01 — presence matrix:** raw IDs produce `none`, `legacy`, `v2`, and
  defensive `both` classifications with the exact stored v2 record version.
- **CL-02 — raw legacy identifiers:** non-v2 legacy ID spelling is accepted for
  classification but rejected by Runtime v2 semantic getters.
- **CL-03 — no adoption:** classification performs no decode, write, migration,
  or cache hit and never manufactures a Runtime v2 State.
- **CL-04 — malformed storage:** missing/wrong legacy object shape, unsupported
  v2 record version, and canceled classification fail closed without changing
  either namespace.

## 8. Query-plan and resource bounds

- **QY-01 — indexed required queries:** `EXPLAIN QUERY PLAN` fixtures prove exact
  StateID, parent, provenance, cache-key, and materialization-page lookups use
  the documented indexes, including the insertion-sequence watermark, with no
  full scan or `MAX` over a growing data table. First-page high water comes from
  `sqlite_sequence` in the same read transaction. Assertions inspect referenced
  tables/indexes rather than matching SQLite's version-dependent plan prose.
- **QY-02 — bounded work:** materialization requests read at most one page plus
  one lookahead row; provenance follows the same row/byte budgets; lineage
  performs at most one indexed parent lookup per State and stops at both the
  semantic and 32-MiB limits; corrupt fan-out cannot force an unbounded returned
  collection.
- **QY-03 — cancellation:** cancellation while waiting for the sole connection,
  traversing lineage, loading observations, or reading a materialization page
  returns `context.Canceled`/`DeadlineExceeded` with no partial values or writes.

## 9. Stability, fuzzing, and coverage gates

- **GX-01 — default-path regression:** current prepare/run/delete/ls/cache
  behavior and outputs remain unchanged. Startup may install/verify the dormant
  v2 schema, but instrumentation proves current product flows perform no v2
  semantic read, write, cache hit, or materialization selection.
- **GX-02 — restart acceptance:** one file-backed scenario stores resolution,
  recipe and relative lineage, multiple provenance observations, and multiple
  materializations, then reopens and verifies the complete graph.
- **GX-03 — rc.6 acceptance:** one fixture-driven scenario proves upgrade,
  legacy diagnostics, v2 isolation, rollback-safe failure, and unrelated-data
  preservation together.
- **GX-04 — fuzzing:** value-returning decoders never panic, accept trailing
  data, or return partial values for cache records, semantic storage envelopes,
  materialization metadata/cursors, and classification IDs. Receiver-based
  decoders additionally prove an existing value is unchanged on failure.
- **GX-05 — race suite:** in-process state/provenance/cache/materialization reads
  and writes pass `go test -race`; this does not stand in for process-lock tests.
- **GX-06 — coverage:** measure runtime-go resolver and local-engine packages
  separately with per-line reports. Target is 100%; minimum accepted coverage is
  95% for every changed package. Any deficiency follows the repository's
  documented approval loop before additional tests or dead-code removal.
- **GX-07 — external lock fail-fast:** a subprocess holds the database write
  lock while direct and managed constructors/writes are attempted. Instrumented
  assertions prove `busy_timeout=0`, no retry/sleep, prompt `SQLITE_BUSY`, and no
  mutation; this intentionally catches the current managed-startup timeout
  contradiction before implementation can be accepted.

No CLI or OpenAPI tests are added because #110 introduces no such surface.
Existing tests are reviewed for contradictions only after this list is approved.
