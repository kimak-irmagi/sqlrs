# #89: перенос замеров скорости в GitHub Actions

Статус: предложение после разбора и исправлений; ожидается утверждение компонентов
и платформы. 2026-11-08 @evilguest попросил убрать нагрузку с ноутбука, сохранив
полный протокол скорости, если его поддерживает Actions. Само это предложение
ещё не разрешает писать код запуска и стенда; перечень тестов согласуется отдельно.

## Граница и платформа

Использовать стандартные виртуальные машины GitHub `ubuntu-24.04`, x64, для
публичного sqlrs. Обе версии движка запускать последовательно на одной машине,
а не раскладывать их по разным заданиям матрицы. Эталон остаётся настоящим
v0.1.1-rc.7, но берётся опубликованный Linux/amd64: Liquibase на хосте против
Liquibase в контейнере. Не объединять эти времена с наблюдениями Windows ноутбука.
Функциональные проверки Windows сохраняются отдельно.

Закреплённая контрольная сумма опубликованного архива Linux:
`da6132c95185f2a11561628458d34b22e7cb928c574d8ecec9f06d44fc8d0f01`.
До запуска проверить её и происхождение релиза. Тег/исходники должны соответствовать
`cab99c4c7ced5b18f4dc43a65b002d84d8fef02d`; также записать хеш и сведения сборки
извлечённого движка. Отсутствующий или несовместимый эталон — отказ, не разрешение
незаметно собрать другую старую версию.

Официальные ограничения проверены 2026-11-08:

- [Стандартные исполнители публичных проектов](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
  получают новую виртуальную машину; стандартное использование публичного проекта
  бесплатно. Платные или собственные исполнители автоматически не подключаются.
- [Работа с Docker-контейнерами](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers)
  использует Linux/Ubuntu. Нынешние Windows-стенд и бинарник нельзя просто скопировать
  в Linux: нужен отдельно проверенный перенос путей и запуска на хосте.
- [Предел задания GitHub](https://docs.github.com/en/actions/reference/limits) —
  шесть часов. Вся парная серия и её контроль шума остаются на одной машине.
  Независимое подтверждение может идти на другой новой машине со своим контролем.
  Истечение времени или недостаточный запас оставляют проверку незавершённой;
  нельзя разбить одну серию между машинами и назвать объединение сравнением
  на одном хосте.

## Порядок работы

1. Только явный запуск. После появления файла на основной ветке поддержать ручной
   запуск, а для начала работы в #175 — запуск по метке PR того же репозитория.
   Не сливать незавершённую фичу только ради регистрации рабочего процесса.
   Не запускать дорогие замеры на каждое обычное изменение или чужой PR.
2. Права репозитория — только чтение. Собрать новую версию из точного SHA вершины
   PR, не неопределённого результата слияния; получить закреплённый релиз Linux.
   До измерения подготовить входы, JDBC, образы Liquibase и Java. Примеры только
   общедоступные: jhipster, mobilitydata-user и mobilitydata-main (102 изменения).
3. Выполнить короткую проверку совместимости Linux с обоими настоящими внешними
   движками и независимым эталоном БД. До длинной серии проверить сам стенд и
   оценить, помещается ли крупнейшая серия в предел GitHub. Явно выбрать у обоих
   движков один поддерживаемый способ снимков через копирование, без скрытого
   сравнения разных файловых систем/способов. Это не зачётный замер. Если релиз
   не поддерживает такую настройку, совместимость не подтверждена; новый режим
   продукта ради эталона не добавляется.
4. Для каждого примера последовательно выполнить прежние утверждённые P01b пары
   с чередованием и контроль шума на одной машине. Образы прогреть вне измеряемого
   интервала; проход без кэша получает новое хранилище, следующий проход с кэшем —
   то же хранилище. Рядом с измеряемыми командами нет сборок и другой нагрузки.
5. Независимое подтверждение выполняется на новой машине с теми же объявленными
   артефактами/настройками и собственным контролем шума. Сравнение — внутри каждой
   машины, не абсолютные времена ноутбука/облака или разных виртуальных машин.
6. Сохранить обезличенные выборки, точные идентичности, сведения исполнителя/образа/
   CPU/памяти/Docker/Java, число контейнеров/CLI и результаты эталонов. Всегда
   убирать точные ресурсы теста. Не публиковать хранилища БД, engine.json, DSN,
   пароли, закрытый SQL-вывод или неотфильтрованные журналы движка.
7. Разобрать собранные данные по прежнему правилу P01b. Зелёное задание сбора
   означает полный корректный сбор, а не автоматическую приёмку скорости.
   Пропущенные, оборванные или неясные результаты не закрывают #89. Перенос
   исполнителя не сокращает протокол и не отменяет требование скорости.

Если предварительная оценка показывает, что вся серия с контролем не помещается
в шесть часов, сообщить об этом до бессмысленного длинного запуска. Отдельная
машина вне ноутбука или изменение протокола тогда потребуют нового решения;
ни один вариант не выбирается молча.

Новая виртуальная машина убирает пользовательскую нагрузку ноутбука, но не обещает
полного отсутствия облачного шума. Контроль сохраняется; шумный или неясный
результат не считается успехом.

## Компоненты и владение данными

- Отдельный процесс Actions отвечает за явный запуск, права чтения, одновременные
  запуски, подготовку артефактов, машины примеров, сроки и хранение отчётов.
- Собственный внешний стенд в `test/performance/liquibase` отвечает за настоящий
  запуск движков/API, примеры/эталоны, изолированные хранилища, монотонное время,
  точный учёт событий Docker и уборку. Переносится проверенное поведение прежнего
  Windows-стенда; зависимости от исходного дерева прототипа не будет. Новых
  точек подмены или экспериментальных путей в продуктовых пакетах нет.
- Небольшие средства в `scripts/performance` проверяют хеши/ревизии, сохраняют
  выборки/происхождение и проверяют полноту. Успешный сбор данных сам по себе
  не даёт им права объявить выполнение требования скорости.
- БД, настройки и вывод остаются закрытыми внутри задания и там удаляются.
  Артефактами становятся только обезличенные доказательства. Общего хранилища,
  изменений API или схемы БД нет.

Старые продуктовые тесты и стенды этим утверждением не переписываются. Для переноса,
ограничений запуска и проверки доказательств нужен отдельный рассмотренный план тестов.

## Критический и повторный разбор

- P1: Windows-бинарник и запуск не подтверждают Linux. Закрепить настоящий релиз
  Linux, проверить совместимость до замеров и разделять платформенные результаты.
- P1: разные движки в разных заданиях означают разные машины. Целую парную серию
  и контроль держать на одной машине; подтверждение получает собственный контроль.
- P1: предел времени может обрезать пример из 102 изменений. Сначала оценка,
  запас на уборку/отчёты и честная незавершённость вместо успешного результата.
- P1: успех Actions можно перепутать с выполнением порога. Разделить сбор данных
  и разбор P01b, сохранить прежние состояния отказа и неопределённости.
- P1: публичный отчёт может раскрыть подключения/SQL. Разрешённый набор полей,
  закрытые исходные данные и уборка только точных ресурсов задания.
- P2: одного workflow_dispatch недостаточно для новой ветки. Предусмотреть
  явно запрошенный запуск по метке PR своего репозитория без преждевременного слияния.
- P2: Linux может незаметно сменить способ снимков или считаться средой без шума.
  В пробном запуске проверить одинаковое копирование и сохранить контроль шума.

Повторный разбор не выявил оставшихся P0–P2 в этом проекте переноса/компонентов.
Совместимость Linux, запас времени и настоящая приёмка ещё не доказаны: нужны
утверждённые тесты и фактический удалённый пробный запуск.
