## Происхождение и проверка

Запуск [42479055486](https://github.com/kimak-irmagi/sqlrs/actions/runs/42479055486),
закреплённые исходники кандидата `668d5050ad154c1967bea4c6e40b91f3a703d5ba`.
Исходники настоящего выпущенного Linux v1 — `cab99c4c7ced5b18f4dc43a65b002d84d8fef02d`.
SHA256 бинарников: v1 `b34c358d2d1e6e969f17d4e393641dd7cb53167870b8e4674db1381bf410bbca`,
v2 `1367bce9ddaa44c0aa378b07c015dfb20a4c0d29f00d2f5a893905686fae14b0`.
Оба пути используют один закреплённый JDBC и снимки `copy`. Реальные различия
Java на хосте/в контейнере явно сохраняются в выборках.

Замечание к сборщику: запрос Linux v1 исполняет `distribution/liquibase`, но
учёт запускного скрипта читает `liquibase.bat`. Это дефект происхождения данных
наблюдателя, не доказанная причина замедления v2. Время API, эталон БД, попадания
в кэш и наблюдения Docker/CLI не берутся из этого хеша; замедление наблюдается,
но происхождение Linux-скрипта и производные числа JVM полностью не подтверждены.
Исходные байты доказательств сохраняются; перед использованием этих метаданных
в отдельной диагностике проверить реально исполняемый Linux-скрипт и процессы.

Каждая разобранная серия прошла существующий `validateCohort`: 20 отдельных
запусков движка, пять чередующихся пар v1/v2 и пять контрольных v1/v1, два прохода
каждого запуска, точные порядок/машина/идентичность и независимые полные проверки
БД/кэша/очистки. Артефакты двух фаз каждого примера дополнительно сравнены
и совпадают; ID машин различаются, как требуется. Время разных машин не смешивается.

## Завершённые серии

Все значения — секунды. Столбцы v1/v2 — описательные медианы путей; столбец
решения — **медиана пяти парных разностей v2 минус v1**, не разность этих медиан.
Последний столбец — максимальная абсолютная разность отдельной контрольной пары
v1/v1, консервативная наблюдаемая граница. Замедление превышает даже эту границу
на обеих независимых машинах; вывод не зависит от выбора меньшей границы по
контрольной медиане.

результат, засчитанный быстрым. Успех примера со 102 изменениями не отменит
подтверждённые отказы других обязательных примеров.

## Наблюдения, пока не причинный профиль

- Оба движка запускают один CLI планирования плюс CLI на каждое изменение
  без кэша; при полном кэше планировщик всё ещё запускается. Быстрый путь
  без повторного планирования — отдельная #104, он не включается молча в #89.
- V2 дополнительно запускает один CLI/контейнер проверки образа на каждый
  запрос, включая кэшированный. Это наблюдение, а не предположение о нуле запусков.
- Созданий контейнеров: v1 4/2, v2 8/4 (без кэша/с кэшем) для обоих примеров
  из 8 и 12 изменений. Это исключает объяснение «контейнер на каждый changeset»
  в этих сериях, но не приписывает секунды отдельной операции.
- Чтение исходников подтверждает разрешение/проверку образа до планирования
  и подготовку среды планирования до принятия полного попадания в кэш состояний.
  Дополнительные контейнеры/проверка — возможный источник постоянных накладных
  расходов, не измеренное причинное объяснение. Оптимизации/контракт не меняются.
