## Что доказывает трасса, а что — нет

Трассировка существенно и по-разному меняет длительность маршрутов:
средняя добавка без кэша +17,784 с для v1 и +10,482 с для v2 относительно
обычных запусков соответствующей версии; с кэшем +2,759/+2,148 с.
Это описательные разности, не поправка, которую можно вычитать из каждого
интервала. Java хоста у v1 трассируется, Java внутри контейнера v2 — нет.
Почти одинаковые полные времена под трассировкой (62,426/63,451 с) поэтому
**не опровергают** обычную регрессию и не доказывают ускорение JVM v2.

Оба прохода без кэша под трассировкой каждой версии имеют одинаковые счётчики:

| Категория | v1 | v2 |
| --- | ---: | ---: |
| Неуточнённый Docker exec | 44 | 71 |
| Docker inspect | 1 | 47 |
| Docker copy | 0 | 28 |
| Вызовы пошагового помощника | 0 | 15 |
| Docker run | 4 | 6 |

Это не все команды. В `other` входят неразобранные команды, а `docker.step`
смешивает применение изменения и проверку удаления прежнего вывода. Нельзя
считать это 15 миграциями: независимые счётчики нагрузки подтверждают восемь
изменений и девять запусков CLI миграций (планирование и восемь шагов) у обеих
версий. v2 дополнительно один раз запускает CLI для проверки состава образа.
С кэшем у каждой версии один CLI миграций; у v2 также CLI проверки образа.

Места дополнительной работы, подтверждённые исходниками закреплённой v2:

- `bindFreshContainerLiquibase` вызывает `InspectRunnerImage` для каждого
  впервые привязываемого задания. Контейнер без сети выполняет `java -version`,
  `liquibase --version` и вычисляет хеши кандидатов JDBC. Обычная фаза привязки
  v2 занимает 1,35–1,67 с без кэша и 1,06–1,09 с с кэшем, но это **вся фаза**,
  не отдельное время проверки образа. Повторное чтение привязки того же задания
  не означает переиспользования проверки образа между заданиями.
- `InspectNamedContainer` выполняет `container ls` и `container inspect`.
  `ReadCompleteLiquibaseStepOutput` проверяет родителя до/после трёх отдельных
  `docker cp` и проверки отсутствия дочерних процессов. `invokeStep` также
  проверяет родителя перед исполнением.
- Для следующих шагов `VerifyLiquibaseCapturePruned` добавляет две проверки
  родителя, две проверки отсутствия дочерних процессов и вызов `probe-prune`.
  Это объясняет по исходникам превышение числа вызовов помощника над числом
  миграций, но нынешний отчёт не разделяет эти режимы и роли обычного exec.

Под трассировкой inspect v2 суммарно занимает 1,238–1,244 с, копирование —
0,760–0,803 с. Это полные времена категорий под наблюдением, **не оценка
устранимого времени обычного запуска**. Пересекающиеся интервалы оболочки/Java
нельзя складывать как независимые расходы. Не покрыто объединением интервалов
10,387–10,626 с у v2 и 11,410–11,585 с у v1 без кэша; с кэшем
2,386–2,413/1,742–1,826 с. Остаток включает работу движка и промежутки,
а не измеренную категорию SQLite, файловой системы или процессора.

## Ревью и следующая граница

Разбор исключил: обвинение последней фазы без учёта переноса запуска БД;
сложение пересечений; подсчёт проверок помощника как JVM; приписывание всей
привязки проверке образа; объявление остатка затратами SQLite; опровержение
обычного замедления равенством трассируемых времён. Повторное ревью оставшихся
P0–P2 в этом отчёте не выявило. Полная точная причина регрессии ещё не установлена;
оптимизация и готовность к слиянию не заявляются.

Узкий следующий шаг наблюдения — разделить **уже захваченные** аргументы команд
на фиксированные роли: управление БД, проверка образа, применение/проверка
помощника, получение списка контейнеров. Без нового синтаксиса трассы и
измерительных вставок в продукт. Границу компонентов и новые тесты нужно
утвердить отдельно до кода. Кандидаты исправления после уточнения — повторное
использование проверенного состава неизменяемого образа и сокращение лишних
обращений Docker с сохранением точной идентичности, целостности закрытого вывода
и полномочий очистки. Они не утверждены и не объявлены достаточными.

Последующее решение (2026-11-10): после обсуждения ограничений @evilguest выбрал
сократить доказанную повторную работу и добавить измерение затрат конкретного
кода, а не требовать сначала ещё одну серию с доработанным strace. См.
[новое предложение компонентов](issue89-cost-attribution-and-trimming.RU.md).
Исторические числа/ограничения выше прежние; точная причинность задним числом
не объявляется установленной.
